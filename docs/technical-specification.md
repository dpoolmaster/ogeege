# 1. Общие сведения

## 1.1. Назначение документа

Документ описывает требования к веб-сервису самостоятельной подготовки школьников к ОГЭ и ЕГЭ по математике. Сервис строится как автоматизированная платформа: нейросети выполняют диагностику, построение плана, разбор ошибок и предварительную проверку развёрнутых ответов; человек (методист) вмешивается только в спорных случаях и в контроль качества.

Документ предназначен для:

- проектирования и реализации backend и frontend;
- планирования этапов работ;
- приёмки результата;
- ведения базы знаний по продукту.

## 1.3. Глоссарий

| Термин                 | Значение                                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------------- |
| **Трек**               | Пара «экзамен + предмет»: `oge_math`, `ege_math_profile`, `ege_math_base`                     |
| **КИМ**                | Контрольный измерительный материал; в узком смысле — номер задания в экзаменационном варианте |
| **Номер КИМ**          | Позиция задания в варианте (например, задание 1, задание 20)                                  |
| **Часть 1**            | Задания с кратким ответом, проверяются автоматически                                          |
| **Часть 2**            | Задания с развёрнутым ответом, проверяются по критериям                                       |
| **Рубрика**            | Набор критериев оценивания задания части 2 с максимальными баллами                            |
| **Первичный балл**     | Сумма баллов за задания варианта до перевода                                                  |
| **Тестовый балл**      | Результат перевода первичного балла в 100-балльную шкалу (ЕГЭ профиль)                        |
| **Оценка**             | Результат перевода первичного балла в 5-балльную шкалу (ОГЭ, ЕГЭ база)                        |
| **Диагностика**        | Короткая сессия для оценки текущего уровня и построения карты пробелов                        |
| **Пробник**            | Полная экзаменационная сессия с таймером и структурой реального экзамена                      |
| **Практика**           | Тематическая сессия по выбранным темам/номерам КИМ                                            |
| **Карта пробелов**     | Оценка освоения по темам и номерам КИМ                                                        |
| **Освоение (mastery)** | Число от 0 до 1, оценка вероятности правильного решения задания темы                          |
| **Прогноз балла**      | Расчёт ожидаемого первичного/тестового балла на дату экзамена                                 |
| **AI-review**          | Черновик проверки развёрнутого ответа, сформированный нейросетью                              |
| **Human-in-the-loop**  | Обязательная или выборочная проверка решения человеком                                        |
| **Freemium**           | Бесплатный базовый доступ с платными расширениями                                             |
| **Entitlement**        | Право пользователя на платную возможность, вычисляемое по подписке                            |

# 2. Цели и границы

## 2.1. Цели продукта

| ID | Цель | Измеримый признак |
|---|---|---|
| G-01 | Дать ученику полный цикл самостоятельной подготовки | ученик проходит путь «регистрация → диагностика → план → практика → пробник → разбор → прогресс» без участия человека |
| G-02 | Максимально автоматизировать проверку и обратную связь | не менее 90% кратких ответов проверяются автоматически; развёрнутые ответы получают AI-черновик в течение 60 секунд |
| G-03 | Снизить участие методиста до контроля качества | методист работает только с очередью review и выборочным аудитом, а не с потоком всех работ |
| G-04 | Дать прозрачный прогресс ученику и родителю | ученик и родитель видят освоение тем, результаты пробников и прогноз балла |
| G-05 | Обеспечить готовую коммерческую модель | freemium + подписка на трек через YooKassa |
| G-06 | Обеспечить расширяемость на другие предметы | добавление предмета не требует изменения кода учебного цикла |

## 2.2. Границы MVP (этап 1)

Входит в MVP:

- три трека: ОГЭ математика, ЕГЭ математика профиль, ЕГЭ математика база;
- открытая регистрация по email с подтверждением;
- онбординг с выбором трека, даты экзамена, цели по баллу и недельного времени;
- диагностика и карта пробелов;
- персональный недельный план;
- теория в виде текстовых материалов;
- банк заданий с фильтрами;
- тематическая практика с автопроверкой;
- пробники с таймером;
- проверка части 2: AI-черновик + очередь методиста;
- разбор ошибок и рекомендации по повторению;
- статистика прогресса и прогноз балла;
- кабинет родителя (минимальный);
- подписка и оплата через YooKassa;
- админка: контент, задания, варианты, рубрики, шкалы, промпты, очередь review, пользователи, подписки;
- email- и in-app-уведомления.

Не входит в MVP (этап 2 и далее):

- видеоуроки и вебинары;
- живые кураторы и чат;
- геймификация (монеты, достижения, серии);
- мобильные приложения;
- другие предметы (физика, информатика, русский язык);
- B2B и белая метка;
- олимпиады;
- реферальная программа;
- публичные отчёты по ссылке;
- SMS и push-уведомления;
- мультиязычность.

## 2.3. Принципы реализации

| ID | Принцип | Следствие |
|---|---|---|
| P-01 | Автоматизация по умолчанию | любой процесс сначала проектируется без человека; человек добавляется как контроль |
| P-02 | AI-first + human-in-the-loop | AI формирует результат, человек подтверждает спорное |
| P-03 | Простота | минимум зависимостей, стандартная библиотека, явный код |
| P-04 | Прозрачность | все оценки и прогнозы объяснимы и воспроизводимы |
| P-05 | Модульность | модульный монолит с изолированными схемами БД |
| P-06 | Конфигурируемость контента | структура экзамена, шкалы и критерии живут в БД, а не в коде |
| P-07 | Идемпотентность | платежи, вебхуки и завершение сессий не создают дублей |
| P-08 | Безопасность несовершеннолетних | минимизация ПДн, согласия, контроль доступа |

## 2.4. Не-цели

- Замена школы или репетитора.
- Выдача официальных результатов экзамена.
- Гарантия балла.
- Полностью автоматическая итоговая оценка развёрнутых ответов без возможности апелляции.
- Хранение видео и организация прямых трансляций.

# 4. Пользовательские сценарии

## 4.1. Сквозной сценарий ученика

```
1. Гость открывает SEO-страницу трека
2. Проходит демо-диагностику (5-7 заданий) без регистрации
3. Видит предварительный результат и предложение зарегистрироваться
4. Регистрируется, подтверждает email
5. Онбординг: трек, дата экзамена, цель по баллу, время в неделю
6. Полная диагностика
7. Получает карту пробелов и недельный план
8. Ежедневно: теория -> практика -> разбор ошибок
9. Раз в 2 недели: контрольный пробник
10. Раз в неделю: пересчёт плана
11. Видит прогресс и прогноз балла
12. Приглашает родителя
13. При исчерпании бесплатных лимитов видит предложение подписки
14. Оплачивает подписку через YooKassa
15. Продолжает подготовку с полным доступом
```

## 4.2. Сценарий диагностики

| Шаг | Действие системы | Результат |
|---|---|---|
| 1 | выбор трека | трек зафиксирован в профиле |
| 2 | подбор заданий | стратифицированная выборка по номерам КИМ |
| 3 | прохождение | ответы сохраняются по одному |
| 4 | завершение | рассчитывается карта пробелов |
| 5 | анализ | AI формирует текстовые рекомендации |
| 6 | планирование | создаётся недельный план |

Требования к выборке диагностики:

- покрытие всех номеров КИМ трека;
- минимум одно задание на номер;
- суммарная длительность не более 45 минут;
- сложность распределена от базовой к повышенной;
- задания части 2 включаются только если трек их содержит и включена проверка части 2.

## 4.3. Сценарий практики

```
выбор темы или автоматический выбор по плану
        |
        v
сессия практики (10-20 заданий, без таймера или с мягким лимитом)
        |
        v
ответ на задание -> мгновенная автопроверка (часть 1)
        |
        +--> часть 2 -> AI-черновик -> при низкой уверенности очередь методиста
        |
        v
результат сессии -> обновление освоения -> разбор ошибок -> рекомендации
```

## 4.4. Сценарий пробника

| Шаг | Требование |
|---|---|
| Старт | фиксируется дедлайн на сервере; клиентский таймер информационный |
| Прохождение | навигация по заданиям, сохранение ответов, отметка заданий |
| Завершение | ручное или автоматическое по дедлайну |
| Проверка части 1 | автоматически сразу после завершения |
| Проверка части 2 | AI-черновик, затем решение методиста или автопринятие при высокой уверенности |
| Результат | первичный балл, тестовый балл или оценка, разбор по номерам КИМ |
| Апелляция | ученик может оспорить оценку задания части 2 |

## 4.5. Сценарий родителя

```
получает письмо-приглашение
        |
        v
регистрируется или входит
        |
        v
подтверждает привязку

        |
        v
принимает, корректирует или отправляет на повторную проверку
        |
        v
решение фиксируется в аудите и уходит ученику
```

## 4.7. Сценарий администратора

```

просмотр платежей и вебхуков

```

## 4.8. Сценарий оплаты

# 5. Функциональные требования по модулям

Каждый модуль владеет своей схемой PostgreSQL, своим repository и своей бизнес-логикой. Взаимодействие между модулями — только через интерфейсы, объявленные потребителем.

## 5.1. Модуль `publicsite`

**Назначение:** публичные страницы, SEO, открытый банк заданий, демо-диагностика, лид-формы, статьи.

**Схема:** `public`

### Таблицы

| Таблица | Назначение |
|---|---|
| `public.articles` | статьи и разборы (slug, title, content_md, status, published_at) |
| `public.leads` | заявки с публичных форм |
| `public.seo_pages` | метаданные SEO-страниц (slug, title, description, og) |

### Требования

| FR-LEARN-12 | Ограничения freemium | проверка прав перед стартом платной сессии |

### Правила расчёта освоения

Освоение темы рассчитывается как экспоненциально взвешенная доля правильных ответов с учётом сложности:

```
mastery_new = mastery_old * (1 - alpha) + correct * alpha * difficulty_factor
alpha = 0.3
difficulty_factor = 1.0 для базового, 1.1 для повышенного, 1.2 для высокого
mastery ограничивается диапазоном [0, 1]
```

При количестве попыток меньше 3 освоение считается недостоверным и помечается флагом `low_confidence`.

### Правила интервального повторения

```
при успехе: interval = min(interval * ease, 60), ease = min(ease + 0.1, 2.5)
при неудаче: interval = 1, ease = max(ease - 0.2, 1.3)
начальный interval = 1, ease = 2.0
next_review_at = last_practiced_at + interval дней
```

### Приоритет темы для плана

```
priority = topic_weight * (1 - mastery) * confidence_factor * recency_factor
topic_weight = доля максимального первичного балла, приходящаяся на тему
confidence_factor = 1.0 при попытках >= 3, иначе 1.2
recency_factor = 1.0 + 0.2 * (1 - mastery) при давности более 14 дней
```

### Алгоритм прогноза

```
expected_primary = сумма по номерам КИМ (p_n * max_points_n)
p_n = освоение номера КИМ с поправкой на сложность заданий
predicted_test = score_scales[round(expected_primary)]
confidence = f(число попыток, покрытие номеров КИМ, разброс результатов)
interval = predicted ± z * standard_error
```

Правила:

- при покрытии менее 50% номеров КИМ прогноз помечается `low_confidence`;
- при отсутствии данных прогноз не показывается, вместо него — приглашение пройти диагностику;
- AI формирует только текстовое объяснение, числа считаются детерминированно.

Направление стрелки: потребитель → провайдер. Циклов нет.

Интерфейсы объявляет потребитель. Примеры:

type ContentProvider interface {

    HasFeature(ctx context.Context, userID uuid.UUID, feature string) (bool, error)

    GetDecision(ctx context.Context, reviewID uuid.UUID) (Decision, error)

## 6.5. Сборка зависимостей

Все связи собираются только в `cmd/server/main.go`. Модуль не импортирует сервис другого модуля напрямую, кроме интерфейса, объявленного у себя.

## 6.6. Транзакции

- Транзакции создаются только в Service.
- Repository получает `pgx.Tx` или пул и не управляет транзакцией.
- Межмодульные операции не выполняются в одной транзакции; используется outbox или eventual consistency.
- Пример: оплата и активация подписки выполняются в одной транзакции модуля `billing`; уведомление отправляется через outbox.

## 6.7. Фоновые задачи

Реализуются на PostgreSQL без внешней очереди.

| Задача | Периодичность | Описание |
|---|---|---|
| `email_outbox` | каждые 10 секунд | отправка писем |
| `session_deadline` | каждую минуту | завершение сессий по дедлайну |
| `review_escalation` | каждые 5 минут | эскалация просроченных задач |
| `weekly_replan` | ежедневно ночью | пересчёт планов на новую неделю |
| `weekly_report` | раз в неделю | формирование и отправка отчётов |
| `progress_recalc` | после сессии и ночью | пересчёт статистики и прогнозов |
| `ai_budget_reset` | ежедневно | сброс суточного бюджета AI |
| `cleanup_tokens` | ежедневно | удаление истёкших токенов и сессий |

Механизм: таблица задач с `status`, `scheduled_at`, `locked_at`, `attempts`; воркеры берут задачи через `FOR UPDATE SKIP LOCKED`.

# 9. AI-контур

## 9.1. Назначение

AI-контур решает три задачи:

1. проверка развёрнутых ответов части 2 с оценкой по критериям;
2. объяснение ошибок и рекомендации по повторению;
3. текстовая интерпретация прогресса и плана.

Все числовые расчёты (баллы, освоение, прогноз) выполняются детерминированно в коде. AI не вычисляет итоговые числа.

## 9.2. Архитектура

```
learning/service
      |
      v
ai.Service
      |
      +--> PromptRepository (БД)
      +--> RequestRepository (БД)
      +--> Provider (OpenAI-совместимый HTTP-клиент)
      +--> BudgetGuard
      +--> SchemaValidator
```

## 9.3. Конфигурация

| Переменная | Назначение | Обязательна |
|---|---|---|
| `AI_BASE_URL` | базовый URL провайдера | да |
| `AI_API_KEY` | ключ доступа | да |
| `AI_MODEL` | имя модели | да |
| `AI_TIMEOUT_SECONDS` | таймаут запроса | да |
| `AI_MAX_RETRIES` | число повторов | да |
| `AI_TEMPERATURE` | температура | да |
| `AI_MAX_TOKENS` | лимит токенов ответа | да |
| `AI_DAILY_BUDGET` | дневной лимит стоимости | да |
| `AI_CONFIDENCE_AUTO_APPROVE` | порог автопринятия | да |
| `AI_CONFIDENCE_HUMAN` | порог обязательной проверки | да |
| `AI_ENABLED` | глобальный выключатель | да |

## 9.4. Протокол

Запрос:

```http
POST {AI_BASE_URL}/chat/completions
Authorization: Bearer {AI_API_KEY}
Content-Type: application/json

{
  "model": "{AI_MODEL}",
  "temperature": 0.2,
  "max_tokens": 2000,
  "response_format": {"type": "json_object"},
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."}
  ]
}
```

Требования к совместимости:

- поддержка `messages`;
- поддержка `response_format` типа `json_object`; если провайдер не поддерживает, выполняется fallback на строгую инструкцию формата и последующий разбор JSON;
- корректная обработка кодов 429 и 5xx с ретраем;
- таймаут на уровне клиента.

## 9.5. Шаблоны промптов

| Код | Назначение | Вход | Выход |
|---|---|---|---|
| `check_extended_answer` | проверка части 2 | условие, ответ ученика, рубрика, эталонное решение | JSON оценки по критериям |
| `explain_error` | объяснение ошибки | условие, ответ ученика, правильный ответ, тема | текст объяснения и рекомендация |
| `session_summary` | разбор сессии | результаты по номерам КИМ, темы | текст сводки |
| `plan_comment` | комментарий к плану | карта пробелов, дата экзамена | текст комментария |
| `forecast_comment` | комментарий к прогнозу | числа прогноза, слабые темы | текст комментария |

## 9.6. Схема ответа проверки

```json
{
  "verdict": "correct",
  "awarded_points": 2,
  "max_points": 2,
  "confidence": 0.91,
  "criteria": [
    {
      "code": "C1",
      "met": true,
      "points": 1,
      "max_points": 1,
      "comment": "Обоснование перехода выполнено"
    }
  ],
  "feedback_md": "Решение верное. Обрати внимание на оформление обоснования.",
  "error_tags": [],
  "needs_human": false,
  "reasoning_summary": "Все критерии выполнены"
}
```

Правила валидации:

- `verdict` одно из `correct`, `partial`, `incorrect`, `unclear`;
- `awarded_points` в диапазоне от 0 до `max_points`;
- `confidence` от 0 до 1;
- сумма баллов по критериям равна `awarded_points`;
- при `verdict = unclear` обязательно `needs_human = true`;
- при несоответствии схеме ответ отклоняется и выполняется повтор.

## 9.7. Правила уверенности

```
confidence >= AI_CONFIDENCE_AUTO_APPROVE   -> автопринятие, выборочный аудит
AI_CONFIDENCE_HUMAN <= confidence < порог  -> автопринятие с повышенной долей аудита
confidence < AI_CONFIDENCE_HUMAN           -> обязательная очередь методиста
```

Дополнительно в очередь методиста попадают:

- апелляции ученика;
- ответы с `verdict = unclear`;
- ответы, где AI изменил балл относительно первичной проверки;
- случайная выборка автоматически принятых работ с настраиваемой долей.

## 9.8. Защита от галлюцинаций

| ID | Мера |
|---|---|
| AI-20 | В промпт передаётся только условие, ответ, рубрика и эталонное решение. |
| AI-21 | Запрещено просить модель придумывать критерии: критерии приходят из БД. |
| AI-22 | Ответ модели проверяется по схеме и арифметике баллов. |
| AI-23 | При отсутствии эталонного решения задание не отправляется на автоматическую проверку. |
| AI-24 | Модель обязана вернуть `unclear`, если данных недостаточно. |
| AI-25 | Все ответы сохраняются для последующего аудита и сравнения версий. |

## 9.9. Стоимость и лимиты

- Стоимость считается по тарифу модели из конфига.
- Дневной бюджет проверяется перед запросом.
- При превышении бюджета запросы не отправляются, работы попадают в очередь методиста.
- Метрики: число запросов, доля ошибок, средняя задержка, стоимость за день.

## 9.10. Деградация

```
провайдер недоступен
        |
        v
повтор с задержкой
        |
        +--> успех -> обычный путь
        |
        +--> исчерпаны повторы
                 |
                 v
        работа помечается "требует проверки"
                 |
                 v
        ученик видит: "ответ принят, проверка займёт больше времени"
```

Учебный цикл без AI продолжает работать: автопроверка части 1, теория, практика и пробники доступны.

# 10. Контент и импорт ФИПИ

## 10.1. Структура треков

| Трек | Код | Часть 1 | Часть 2 | Перевод балла |
|---|---|---|---|---|
| ОГЭ математика | `oge_math` | задания 1–19, краткий ответ | задания 20–25, развёрнутый ответ | первичный → оценка |
| ЕГЭ математика профиль | `ege_math_profile` | задания 1–11, краткий ответ | задания 12–18, развёрнутый ответ | первичный → тестовый |
| ЕГЭ математика база | `ege_math_base` | задания 1–21, краткий ответ | нет | первичный → оценка |

Значения приведены как пример и должны сверяться с актуальной спецификацией ФИПИ. Структура хранится в БД и меняется без правки кода.

## 10.2. Стартовый объём контента

| Параметр | Значение |
|---|---|
| Задания на каждый номер КИМ | не менее 10 |
| Полные варианты на каждый трек | не менее 3 |
| Теория | по каждой теме трека |
| Рубрики части 2 | по каждому номеру части 2 |
| Шкалы перевода | по каждому учебному году |

Итого ориентировочно:

```
ОГЭ:            25 номеров * 10 = 250 заданий + 3 варианта
ЕГЭ профиль:    18 номеров * 10 = 180 заданий + 3 варианта
ЕГЭ база:       21 номер  * 10 = 210 заданий + 3 варианта
------------------------------------------------------------
Банк:           ~640 заданий
Варианты:       9 полных вариантов
```

## 10.3. Источники

| Источник | Использование |
|---|---|
| ФИПИ, открытый банк заданий | основной источник условий |
| ФИПИ, демоверсии и спецификации | структура экзамена, критерии, шкалы |
| Собственные задания методиста | закрытие пробелов, уникальные варианты |
| AI-генерация | черновики, только после проверки методистом |

## 10.4. Процесс импорта

```
1. Методист выбирает трек и учебный год
2. Загружает источник: текст, файл или ручной ввод
3. Система разбирает условие и создаёт черновик задания
4. Система предлагает номер КИМ, тему и тип ответа
5. Методист проверяет условие, ответ, тему и сложность
6. Система проверяет дубликат по хешу
7. Методист публикует задание
8. Задание становится доступно в банке и конструкторе вариантов
```

Требования:

| ID | Требование |
|---|---|
| FR-IMP-01 | Черновик создаётся со статусом `draft` и не виден ученикам. |
| FR-IMP-02 | Импорт не публикует задания автоматически. |
| FR-IMP-03 | Дубликаты определяются по хешу нормализованного условия. |
| FR-IMP-04 | Для каждого задания хранится источник и ссылка. |
| FR-IMP-05 | Формулы хранятся в LaTeX и проверяются на рендер. |
| FR-IMP-06 | Изображения загружаются в S3 и привязываются к заданию. |
| FR-IMP-07 | Импорт пишется в аудит. |

## 10.5. Формат хранения условия

- Markdown;
- формулы в `$...$` и `$$...$$`;
- изображения через ссылки на S3;

- В сессии сохраняется снимок задания.
- Уже начатые сессии не меняются.
- Старые версии доступны администратору.

# 11. Проверка ответов

## 11.1. Классификация ответов

| Тип | Проверка | Модуль |
|---|---|---|
| Краткий числовой | автоматическая | `grading` |
| Краткий текстовый | автоматическая с нормализацией | `grading` |
| Множественный выбор | автоматическая | `grading` |
| Последовательность цифр | автоматическая | `grading` |
| Интервал | автоматическая | `grading` |
| Развёрнутый | AI + человек | `ai`, `review` |

## 11.2. Нормализация

Порядок обработки краткого ответа:

```
1. Обрезка пробелов по краям
2. Приведение всех видов минуса к "-"
3. Замена десятичной запятой на точку
4. Удаление пробелов внутри числа
5. Удаление разделителей тысяч
6. Удаление допустимых единиц измерения
7. Приведение к нижнему регистру, если регистр не важен
8. Сравнение с допустимыми ответами
9. Сравнение с допуском, если задан
```

Примеры:

| Ввод ученика | Эталон | Результат |
|---|---|---|
| `2,5` | `2.5` | верно |
| ` 5/2 ` | `2.5` | верно |
| `- 3` | `-3` | верно |
| `1 000` | `1000` | верно |
| `[-2; 3]` | `[-2;3]` | верно |
| `3; -2` | `-2;3` (порядок не важен) | верно |

## 11.3. Проверка части 2

```
ответ ученика
      |
      v
снимок задания + рубрика + эталон
      |
      v
AI-черновик по критериям
      |
      +--> confidence высокая -> автопринятие + выборочный аудит
      |
      +--> confidence средняя -> автопринятие + повышенный аудит
      |
      +--> confidence низкая  -> очередь методиста
      |
      v
итоговый балл
```

Требования:

| ID | Требование |
|---|---|
| FR-GRADE-20 | Итоговый балл не превышает максимум задания. |
| FR-GRADE-21 | Сумма баллов по критериям равна итоговому баллу. |
| FR-GRADE-22 | Ученик видит разбивку по критериям. |
| FR-GRADE-23 | Ученик видит комментарий и рекомендации. |
| FR-GRADE-24 | Ученик может подать апелляцию в течение 7 дней. |
| FR-GRADE-25 | Апелляция не блокирует дальнейшее обучение. |
| FR-GRADE-26 | Решение методиста имеет приоритет над AI. |

## 11.4. Шкалы перевода

| Трек | Вход | Выход |
|---|---|---|
| `oge_math` | первичный балл | оценка 2–5 |
| `ege_math_profile` | первичный балл | тестовый балл 0–100 |
| `ege_math_base` | первичный балл | оценка 2–5 |

Правила:

- шкала привязана к учебному году;
- минимальный порог хранится отдельно;
- изменение шкалы не меняет уже выставленные результаты;
- в результате сессии сохраняется снимок применённой шкалы.

## 11.5. Пересчёт результата

```
primary_score = сумма awarded_points по всем заданиям
test_score или grade = scale[primary_score]
```

Если задание части 2 ещё на проверке:

- результат помечается `pending_review`;
- показывается предварительный балл по части 1;
- итоговый балл обновляется после завершения проверки.

# 15. Тестирование

## 15.1. Общие требования

| ID | Требование |
|---|---|
| TST-01 | На весь функционал написаны unit-тесты. |

| TST-06 | Интеграционные тесты используют реальный PostgreSQL в Docker. |

## 15.2. Unit-тесты

| Модуль | Что проверяется |
|---|---|
| `grading` | нормализация, допуски, дроби, интервалы, последовательности |
| `learning` | освоение, интервалы повторения, приоритеты, генерация плана |
| `progress` | прогноз, интервалы уверенности, граничные случаи |
| `billing` | идемпотентность, переходы статусов, entitlements |
| `auth` | токены, сроки, отзыв сессий, ограничение попыток |
| `ai` | валидация схемы, пороги уверенности, ретраи, бюджет |
| `review` | приоритеты, назначение, переходы состояний |

## 15.3. Интеграционные тесты

| Сценарий | Проверка |
|---|---|
| регистрация → подтверждение → вход | сессия создаётся, доступ есть |
| онбординг → диагностика → план | план создан, карта пробелов заполнена |
| практика → проверка → освоение | освоение изменилось |
| пробник → таймаут → результат | сессия завершена, балл посчитан |
| часть 2 → AI → очередь → решение | итоговый балл обновлён |
| заказ → платёж → вебхук → подписка | подписка активна, дубль не создаётся |
| родитель → приглашение → прогресс | доступ выдан и отозван |

## 18.6. Приложение F. Состояния сессии

```
created -> in_progress -> submitted -> checking -> checked
                    \-> abandoned
                    \-> expired -> submitted
```

| Состояние | Значение |
|---|---|
| `created` | сессия создана, задания зафиксированы |
| `in_progress` | ученик проходит |
| `submitted` | ответы отправлены |
| `checking` | идёт проверка части 2 |
| `checked` | результат готов |
| `abandoned` | ученик отказался |
| `expired` | истёк дедлайн, ответы отправлены |

## 18.7. Приложение G. Состояния подписки

```
none -> pending -> active -> expired
                  \-> canceled
active -> past_due -> active
```

| Состояние | Значение |
|---|---|
| `none` | подписки нет |
| `pending` | заказ создан, оплата не подтверждена |
| `active` | подписка действует |
| `past_due` | срок истёк, идёт продление |
| `expired` | подписка закончилась |
| `canceled` | отменена |
