## Context

См. `proposal.md` — Why. Текущее состояние, которое определяет подход:

- Публичный контур (`internal/publicsite/views.templ`) и страницы аутентификации (`internal/auth/views.templ`) рендерятся Templ поверх Pico.css v2 с CDN; единственный собственный CSS — `internal/shared/render/assets/app.css`, и он описывает только компактные формы `.auth-page`.
- Pico повышает корневой кегль на широких экранах (`106.25%` при 1024 px, `112.5%` при 1280 px, `118.75%` при 1440 px). Админка это уже компенсирует (`web/admin/src/style.css`: `--pico-font-size: 87.5%`), публичный контур — нет.
- Компонентного слоя нет: разметка собирается из `<article>`, `<ul>`, `<table>` и `<button role="button">`.
- Закрытая часть, кроме входа и регистрации, ещё не реализована; каркас кабинета появится на этапе 4. Значит дизайн-система должна быть заложена до него.
- Ограничения: Templ + HTMX + Pico.css, без Tailwind и без клиентского фреймворка (AGENTS.md, раздел «Frontend»); весь текст на русском; предмет и трек — данные, ветвления по предмету запрещены.

## Goals / Non-Goals

**Goals:**

- Один слой токенов и компонентов, который используют публичный контур, аутентификация, профиль и будущий кабинет.
- Предсказуемая типографика, не зависящая от ширины экрана.
- Обязательные состояния экранов и компонентов, чтобы интерфейс не выглядел «сырым».
- Каркас кабинета и компонент карты пробелов, готовые к этапу 4.
- Бренд как значение конфигурации, а не литерал в шаблонах.

**Non-Goals:**

- Новые маршруты, сценарии и бизнес-логика. Проверка задания прямо на лендинге и пошаговая демо-диагностика — отдельные изменения `public-site` после архивации `stage-3-public-site`.
- Переписывание админки на Vue: она остаётся как есть; общие токены для неё — отдельная задача.
- Тёмная тема, анимации-украшения, геймификация.
- Внедрение UI-фреймворка, CSS-in-JS или утилитарных классов.

## Decisions

### 1. Токены как CSS custom properties поверх Pico

Собственный слой `--v-*` задаётся в `internal/shared/render/assets/app.css`, а переменные Pico переопределяются там же. Файл подключается после `pico.min.css`, поэтому переопределение `:root` выигрывает по каскаду при равной специфичности.

```css
:root {
  --pico-font-size: 15px;
  --pico-line-height: 1.55;
  --v-bg: #f7f5f0;
  --v-surface: #ffffff;
  --v-ink: #1b1b1f;
  --v-ink-2: #4b4b55;
  --v-muted: #7c7c88;
  --v-line: #e6e2d9;
  --v-accent: #2f5bea;
  --v-accent-soft: #e9eefc;
  --v-ok: #1f8a5b;
  --v-ok-soft: #e7f4ed;
  --v-err: #c4453c;
  --v-err-soft: #fbecea;
  --v-warn: #b7791f;
  --v-warn-soft: #fdf2e0;
  --v-r-field: 10px;
  --v-r-card: 14px;
  --v-r-panel: 20px;
}
```

Альтернативы: Tailwind (новый билд-шаг и зависимость, запрещено соглашениями), отдельный CSS-фреймворк (дублирует Pico), инлайн-стили (нет единообразия). Отвергнуты.

Проверка: базовый кегль фиксирован в `px`, поэтому responsive-правила Pico не меняют размер текста; тест-снимок HTML не требуется — достаточно юнит-теста на наличие токенов в собранном CSS не нужен, проверяется визуально и через `grep` в CI-скрипте стилей.

### 2. Шрифт Golos Text, self-hosted

`@font-face` с `font-display: swap` и системным fallback (`-apple-system, Segoe UI, Roboto, sans-serif`). Файлы `woff2` кладутся в `internal/shared/render/assets/fonts/` и раздаются тем же обработчиком статики, что и `app.css`. Альтернативы: CDN (лишняя внешняя зависимость и правка CSP), Inter (обезличенный, как у большинства конкурентов), системный шрифт (не даёт характера). Отвергнуты.

Шкала: `12 · 13 · 15 · 17 · 20 · 24 · 32 · clamp(30px, 4vw, 44px)`. Числа — `font-variant-numeric: tabular-nums`.

### 3. Компонентный слой как Templ-пакет

Новый пакет `internal/shared/render/ui` с типизированными пропсами и классами `v-*`:

| Компонент | Пропсы (минимум) |
|---|---|
| `Button` | `Variant` (primary/secondary/ghost/danger), `Size` (sm/md), `Disabled`, `Loading` |
| `Field` | `Label`, `Name`, `Type`, `Value`, `Hint`, `Error`, `Required` |
| `Card` | `Title`, `Meta`, `Href` |
| `Badge` | `Tone` (neutral/accent/ok/err/warn), `Text` |
| `Tabs` | `Items`, `Active` |
| `Table` | `Head`, `Rows`, `Dense` |
| `Panel` | `Title`, `Side` (right/left) |
| `Modal` | `ID`, `Title`, `Open` |
| `Toast` | `Tone`, `Text` |
| `EmptyState` | `Title`, `Text`, `Action` |
| `Skeleton` | `Lines` |
| `Progress` | `Value`, `Max`, `Label` |
| `Stepper` | `Current`, `Total`, `Label` |
| `ResultPanel` | `Correct`, `Explanation`, `NextHref` |
| `TaskCard` | `KimNumber`, `Topic`, `Excerpt`, `Href` |
| `GapHeatmap` | `Topics`, `KimNumbers`, `Cells` |
| `Breadcrumbs` | `Items` |
| `HelpTip` | `Text` |

Пропсы не содержат предметных полей: цвет и подписи приходят строками/значениями. Альтернатива — только CSS-классы без компонентов: быстрее, но не даёт единообразия и типизации; отвергнута.

### 4. Бренд через конфигурацию

В `internal/shared/config/config.go` добавляется необязательное `BrandName` (`BRAND_NAME`, значение по умолчанию `Верно`) и попадает в единый объект конфигурации. Обработчики передают бренд в шаблонный слой через структуру `Chrome{Brand, Nav, Crumbs}`, а не через глобальную переменную. Альтернативы: константа в пакете (смена = правка кода), литерал в шаблоне (текущее состояние) — отвергнуты.

### 5. Цвет трека — детерминированная палитра

`ui.SubjectTone(code string) Tone` хеширует код трека и выбирает один из фиксированных оттенков; пустой код даёт нейтральный. Ветвлений по предмету нет, миграция БД не нужна, новый трек получает цвет автоматически. Когда в данных появится явный цвет, он заменит вычисление внутри этой функции без изменения вызовов.

### 6. Каркасы

Публичный лендинг (существующие данные и маршруты):

```
+--------------------------------------------------------------+
| brand   Треки  Банк  Демо  Статьи          [Войти] [Начать]   |
+--------------------------------------------------------------+
| ОГЭ · Математика                     +----------------------+ |
| Краткое описание трека               | демо: 7 заданий      | |
| [Пройти демо] [Открыть банк]         | [Начать]             | |
| факты: год · минуты · задания        +----------------------+ |
+--------------------------------------------------------------+
| Как это работает: диагностика -> пробелы -> план             |
+--------------------------------------------------------------+
| Структура экзамена (таблица)        | Записаться (форма)     |
+--------------------------------------------------------------+
| Статьи | FAQ | подвал                                          |
```

Банк — карточки, фильтры в query-строке (уже поддержаны обработчиком):

```
+--------------------------------------------------------------+
| Трек [ ]  Номер КИМ [ ]  Тема [ ]            [Показать]       |
+--------------------------------------------------------------+
| +----------------------------+   +-------------------------+ |
| | 1  Алгебра · КИМ 6         |   | Найдено: N              | |
| | Короткое условие...        |   | Показаны 1–20           | |
| |                 [Решать ->] |   +-------------------------+ |
| +----------------------------+                               |
| [Следующая страница]                                          |
+--------------------------------------------------------------+
```

Задание — две колонки на широком экране, одна на узком; на узком панель ответа `position: sticky; bottom: 0`.

```
+-------------------------------+------------------------------+
| КИМ 6 · Алгебра               | Ваш ответ                    |
| Условие, KaTeX, вложения      | [ .............. ]           |
|                               | [Проверить]                  |
|                               | +--------------------------+ |
|                               | | Верно / Неверно + текст  | |
|                               | +--------------------------+ |
+-------------------------------+------------------------------+
```

Демо — одна страница, карточка на задание, липкий индикатор прогресса:

```
Демо · ОГЭ математика     заполнено 3 из 7  [====------]
+--------------------------------------------------+
| Задание 4 · КИМ 8                                 |
| условие                                           |
| Ответ [ .................... ]                    |
+--------------------------------------------------+
```

Кабинет — каркас, который наполняется этапом 4:

```
+----------+---------------------------------------------------+
| brand    |  <Заголовок страницы>            [профиль] [🔔]   |
|          +---------------------------------------------------+
| Сегодня  |  +----------------+ +----------------+ +--------+ |
| Диагнос. |  | Ближайший шаг  | | Пробелы        | | Цель   | |
| Практика |  +----------------+ +----------------+ +--------+ |
| План     |  Основная область                                 |
| Пробники |                                                   |
| Прогресс |                                                   |
| -------- |                                                   |
| Профиль  |                                                   |
+----------+---------------------------------------------------+
```

Карта пробелов — хитмап: строки темы, столбцы номера КИМ, ячейка — состояние (не было / верно / ошибка), цвет только фоном 8–10% alpha плюс символ или подпись.

### 7. Состояния экранов

| Состояние | Компонент | Правило |
|---|---|---|
| Загрузка | `Skeleton` | Повторяет форму контента, не крутилка на весь экран |
| Пусто | `EmptyState` | Пояснение + действие |
| Ошибка | `ErrorState` (частный случай `EmptyState`) | Текст + «Повторить» |
| Недоступно | `Badge` + `HelpTip` | Причина рядом с действием |
| Успех | `Toast` или `ResultPanel` | Не модалка |
| Валидация | `Field.Error` | Ошибка у поля, `aria-invalid` |

### 8. Доступность

- `:focus-visible` — кольцо 2 px акцентом с отступом 2 px; фокус не удаляется.
- Тач-цели ≥ 44×44 px; на десктопе допускаются 36 px для вторичных действий.
- Контраст текста ≥ 4,5:1; приглушённый текст — не светлее `#7c7c88` на `#f7f5f0`.
- `ResultPanel` рендерится с `role="status"` (верно) и `role="alert"` (неверно).
- Иконки без текста — `aria-hidden` или `aria-label`.
- «Перейти к содержимому» — первая ссылка в DOM.
- `prefers-reduced-motion` отключает переходы.

### 9. Порядок внедрения

1. Токены и шрифт.
2. `ui`-пакет и CSS компонентов.
3. Публичные шаблоны (лендинг, банк, задание, демо, статьи, лид).
4. Аутентификация и профиль на общем каркасе.
5. Каркас кабинета и `GapHeatmap` как компонент без страницы.

Шаг 3 выполняется после архивации `stage-3-public-site`, чтобы не смешивать дельта-спеки.

## Risks / Trade-offs

- **Каскад Pico**: переопределения могут проиграть по специфичности → собственный CSS подключается после Pico, а компоненты используют классы `v-*` без зависимости от внутренних классов Pico.
- **Шрифт**: рост веса страницы и вопросы лицензии → только `woff2`, два начертания, `font-display: swap`, Golos Text распространяется по OFL.
- **Разрастание компонентов**: соблазн сделать универсальный компонент «на всё» → пропсы минимальные, вариант добавляется при втором реальном использовании.
- **Визуальные тесты хрупкие**: снимки HTML ломаются от любой правки → проверяем поведение (наличие `aria-*`, состояний, классов) и вручную мобильные размеры.
- **Смешение с этапом 4**: кабинет начнут делать раньше, чем закроется этап 3 → каркас и компоненты готовятся здесь, страницы — на этапе 4.
- **Бренд как конфиг**: значение по умолчанию может «залипнуть» в проде → `BRAND_NAME` попадает в `.env.example` с пометкой.

## Migration Plan

1. Заархивировать `stage-3-public-site`, затем применить эту смену.
2. Добавить токены и шрифт; проверить, что базовый кегль не меняется на 1024/1280/1440 px.
3. Перевести публичные шаблоны на компоненты без изменения маршрутов, данных и поведения; прогнать существующие тесты `publicsite`.
4. Перевести `auth`/`profile` на общий каркас.
5. Добавить каркас кабинета и `GapHeatmap` с юнит-тестами на `SubjectTone` и рендер компонентов.
6. Откат: изменения локализованы в шаблонах и CSS; возврат к предыдущим шаблонам не требует миграций БД.
