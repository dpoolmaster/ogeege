## Context

См. `proposal.md` — Why. К началу этапа есть рабочая основа: конфигурация (`internal/shared/config`), пул `pgx v5` и helper транзакций (`internal/shared/db`), миграции `000001`–`000005`, HTTP-сервер на Gin с middleware (`internal/shared/httpserver`), `slog`, UUID v7 (`internal/shared/ids`), общий конверт ошибок, рендер Templ и `notify`-outbox. Модуль `auth` даёт роли `methodist`/`admin`, middleware `Auth`/`RequireRole` и `Principal`. Модуль `profile` уже сохраняет учебные цели, но принимает `exam_id` как любой UUID. Схемы модулей созданы миграцией `000001_init`, бизнес-таблиц `content` и `admin` нет.

Ограничения, формирующие подход:

- `AGENTS.md`: модульный монолит, `Handler → Service → Repository`, pgx v5 и ручной SQL без ORM и query builder, транзакции только в Service, UUID v7, `context.Context` первым аргументом, `log/slog`, запрет `os.Getenv` вне пакета конфигурации, интерфейс объявляет потребитель, сборка зависимостей только в `cmd/server/main.go`, только русский язык.
- Границы модулей (ТЗ 6.3): у каждого модуля своя схема; запрещены FK и JOIN между схемами; ссылки только по UUID; чтение чужого модуля только через интерфейс его сервиса.
- ТЗ 6.6: межмодульные операции не выполняются в одной транзакции; согласованность через outbox или eventual consistency.
- ТЗ 7.3 даёт SQL только для части таблиц `content`; структура остальных выводится из 5.4 и общих правил 7.1.
- ТЗ 8.9 перечисляет неполный набор административных маршрутов; CRUD-операции дополняются.
- ТЗ 10.5: условие хранится в Markdown, формулы в `$...$`/`$$...$$`, HTML запрещён, кроме санитизированного результата рендера.
- ТЗ 5.13: SPA не является границей безопасности; сервер проверяет роль и CSRF.

Конфликты требований и принятое решение:

| Конфликт | Решение |
|---|---|
| ТЗ 7.3 не содержит SQL для `theory`, `task_options`, `task_attachments`, `variants`, `variant_tasks`, `rubrics`, `score_scales` | Таблицы строятся по 5.4 и 7.1; недостающие поля выводятся из назначения |
| ТЗ 7.3 хранит у задания одно поле `version`, но 10.6 требует историю версий и доступ к старым версиям | Активная версия остаётся в `content.tasks`, история — в новой `content.task_versions` |
| ТЗ 7.3 задаёт `UNIQUE` по `content_hash`, что мешает повторной публикации версии с тем же условием | Уникальность хеша действует на активные задания; история версий хеш не участвует в ограничении |
| ТЗ 7.3 использует составной PK у `kim_topics`, что противоречит DATA-01 (UUID v7) | Явное исключение: связующая таблица сохраняет составной PK, как в ТЗ; это не сущность с собственным жизненным циклом |
| ТЗ 8.9 не содержит методов изменения и удаления для части сущностей | Добавляются `PATCH`/`PUT`/`DELETE` по тем же путям; контракт расширяется, существующие маршруты не меняются |
| `docs/development-status.md` и design этапа 1 относят FR-ADM-07 к этапу 2, а раздел 16 ТЗ не перечисляет его в задачах | FR-ADM-07 включается в `admin`, так как управление ролями уже поддержано в `auth` |
| `platform-foundation` описывает «базовые заголовки безопасности» без точного CSP | CSP расширяется минимально (`font-src 'self' data:` для шрифтов формул); спека `platform-foundation` не меняется |

## Goals / Non-Goals

**Goals:**

- Дать единый источник учебного контента, достаточный для этапов 3–6, без правки кода при изменении структуры экзамена.
- Дать методисту полный цикл ведения контента: создание, импорт черновиков, проверка, публикация, архивирование, версии.
- Дать административный API и SPA с серверной проверкой ролей, CSRF и аудитом.
- Сохранить модульные границы: `content` и `admin` не читают чужие схемы; `profile` проверяет трек через интерфейс.
- Заложить расширяемость без «абстракций на будущее»: промпты, review, платежи и метрики подключаются на своих этапах.

**Non-Goals:**

- Промпты, их версии и тестовый запуск (FR-ADM-05, этап 7).
- Очередь review и решения методиста по работам (FR-ADM-06, этап 7).
- Подписки, платежи, ручная активация и возвраты (FR-ADM-08, этап 9).
- Метрики и дашборды (FR-ADM-10, этап 10).
- Публичные страницы, открытый банк, SEO, лид-формы (этап 3).
- Снимки заданий в сессиях и учебный цикл (этапы 4–6); здесь только версии, на которые снимок будет ссылаться.
- AI-генерация и NLP-разбор условий; импорт принимает структурированный ввод.
- Полный банк из 640 заданий как инженерная задача: seed даёт структуру и демонстрационный набор, наполнение — работа методиста.

## Decisions

### 1. Структура модулей и границы

```
internal/
  content/
    handler.go      — (нет публичных маршрутов на этом этапе)
    service.go      — сценарии, транзакции, версии, импорт, публикация
    repository.go   — SQL по схеме content
    entity.go       — Exam, ExamYear, KimNumber, Topic, Theory, Task, Variant, Rubric, ScoreScale
    dto.go
    seed/           — команда/пакет стартового контента
  admin/
    handler.go      — HTTP /api/admin/*
    service.go      — оркестрация, проверка прав, аудит
    repository.go   — SQL по схеме admin (audit_log)
    entity.go
    dto.go
  shared/
    storage/        — S3-совместимое хранилище
    markdown/       — рендер и санитизация Markdown
web/
  admin/            — Vue 3 SPA (Vite)
```

`admin` объявляет интерфейсы `ContentAdmin` (операции над контентом) и `UserAdmin` (поиск, блокировка, смена роли); их реализуют `content` и `auth`. `profile` объявляет интерфейс `ExamProvider` (`IsExamAvailable`), реализуемый `content`. Связи собираются только в `cmd/server/main.go`.

Альтернатива: `admin` пишет в схемы `content`/`auth` напрямую. Отвергнута — нарушает границы модулей и рассыпает бизнес-правила по двум местам.

Альтернатива: `admin` — тонкий слой только над `content`, без собственного Service. Отвергнута — аудит и разграничение прав методиста/администратора являются бизнес-логикой `admin`.

### 2. Схема `content`

```
content.exams            id, code UNIQUE, title, subject, status, created_at, updated_at
content.exam_years       id, exam_id, year, duration_minutes, status, created_at, updated_at, UNIQUE(exam_id, year)
content.kim_numbers      id, exam_year_id, number, part, answer_type, max_primary_score, title, created_at, updated_at, UNIQUE(exam_year_id, number)
content.topics           id, exam_id, parent_id, code, title, order_index, created_at, updated_at, UNIQUE(exam_id, code)
content.kim_topics       kim_number_id, topic_id, weight, PRIMARY KEY(kim_number_id, topic_id)
content.theory           id, topic_id, content_md, version, status, updated_by, created_at, updated_at
content.tasks            id, exam_year_id, kim_number_id, topic_id, difficulty, statement_md, answer_spec, answer_display, source, source_ref, status, is_public, content_hash, version, created_by, created_at, updated_at
content.task_versions    id, task_id, version, statement_md, answer_spec, answer_display, difficulty, kim_number_id, topic_id, source, source_ref, created_by, created_at
content.task_options     id, task_id, position, content_md, is_correct
content.task_attachments id, task_id, kind, storage_key, url, alt, created_at
content.variants         id, exam_year_id, title, kind, duration_minutes, status, created_at, updated_at
content.variant_tasks    id, variant_id, position, task_id, points, UNIQUE(variant_id, position), UNIQUE(variant_id, task_id)
content.rubrics          id, kim_number_id, exam_year_id, version, criteria_json, status, created_at, updated_at
content.score_scales     id, exam_year_id, primary_score, test_score, grade, min_threshold, created_at, updated_at, UNIQUE(exam_year_id, primary_score)
```

Индексы: `tasks(kim_number_id, status)`, `tasks(topic_id, status)`, `tasks(is_public, status)`, `UNIQUE tasks(content_hash)`, `task_versions(task_id, version)`, `theory(topic_id, version)`, `variants(exam_year_id, status)`, `rubrics(kim_number_id, exam_year_id, status)`.

Внешние ключи между схемами отсутствуют. Внутри `content` FK допустимы и используются для целостности (`exam_years.exam_id`, `kim_numbers.exam_year_id`, `topics.parent_id`, `tasks.exam_year_id` и т.д.). `parent_id` проверяется на принадлежность тому же треку в Service.

Альтернатива: хранить структуру и задания в JSON-документах. Отвергнута — усложняет фильтрацию, дедупликацию и запросы учебного цикла.

### 3. Версионирование заданий и теории

- `content.tasks` — активная версия задания (форма совместима с 7.3).
- Изменение задания: в одной транзакции Service копирует текущие поля в `content.task_versions` с номером текущей версии, затем обновляет `content.tasks` и увеличивает `version`.
- `content.task_versions` неизменяема; доступ к истории — только через административные операции.
- `content.theory` хранит все версии как строки; активная — опубликованная версия с максимальным номером. Изменение создаёт новую строку.
- Удаление задания запрещено, если есть ссылка из `learning` (проверка через интерфейс появится на этапе 4) или если задание опубликовано; на этом этапе правило реализуется как «опубликованное задание только архивируется».
- `content_hash` считается по нормализованному условию (trim, унификация пробелов, нормализация переносов) через SHA-256; уникальный индекс не даёт создать активный дубликат.

Альтернатива: одна таблица со всеми версиями и флагом `is_active`. Отвергнута — усложняет запросы учебного цикла и уникальность хеша.

### 4. Импорт и дедупликация

- Вход импорта — структурированный JSON-батч (массив черновиков с полями условия, ответа, номера КИМ, темы, сложности, источника) и ручная форма.
- Каждый элемент проходит: валидацию обязательных полей, проверку LaTeX, нормализацию условия, расчёт хеша, проверку дубликата, создание в статусе `draft`.
- Импорт возвращает отчёт: создано, пропущено как дубликат, отклонено с причинами.
- Импорт пишется в аудит одним действием с числом созданных/пропущенных.
- Публикация — отдельная операция, требует роли методиста/администратора.

Альтернатива: парсинг Markdown/PDF с эвристиками. Отвергнута — ненадёжно и относится к AI-контуру этапа 7.

Альтернатива: асинхронный импорт через очередь. Отвергнута — батчи методиста небольшие, синхронная обработка проще и даёт немедленный отчёт.

### 5. Конструктор вариантов

- Ручной режим: список `(task_id, points)` с проверкой принадлежности задач учебному году, отсутствия повторов и непрерывной нумерации позиций.
- Генерация по правилам: набор правил `{kim_number, count, difficulty?, topic_id?}`; отбор заданий из опубликованного банка нужного учебного года; проверка достаточности и отсутствия повторов; при нехватке — отказ без частичного сохранения.
- Случайность выбора инкапсулируется в Service и подменяется в тестах, чтобы результат был воспроизводим.

Альтернатива: генерация на стороне SPA. Отвергнута — правила и целостность должны проверяться на сервере.

### 6. Хранилище изображений

- `shared/storage` — интерфейс `Put(ctx, key, contentType, r)`, `Get(ctx, key)`, `Delete(ctx, key)`; реализация на S3-совместимом клиенте (MinIO локально).
- Ключ формируется сервером (`tasks/{taskID}/{uuid}.{ext}`), клиентское имя файла не используется как ключ.
- Проверка типа по MIME и расширению, размера — константой пакета; при превышении `HTTP_MAX_BODY_BYTES` срабатывает общий middleware.
- Бакет приватный; выдача — через серверный маршрут `/media/{key}` с проверкой allowlist ключей и `Content-Type`.
- `content.task_attachments` хранит `storage_key` и `alt`; `url` — вычисляемый путь выдачи.

Альтернатива: публичный бакет и прямые ссылки. Отвергнута — утечка и невозможность отзыва.

Альтернатива: presigned URL. Отвергнута — усложняет конфигурацию и тесты, для MVP достаточно проксирования.

### 7. Административный API

- Базовый префикс `/api/admin`, группа защищена `Auth` + `RequireRole(methodist, admin)`; отдельные операции (пользователи, аудит) дополнительно требуют `admin`.
- Ресурсы: `exams`, `exam-years`, `kim-numbers`, `topics`, `theory`, `tasks`, `variants`, `rubrics`, `score-scales`, `users`, `audit`.
- Мутирующие методы: `POST`, `PATCH`/`PUT`, `DELETE`; публикация — `POST .../publish`, архивирование — `POST .../archive`, генерация варианта — `POST /variants/generate`, импорт — `POST /tasks/import`.
- Списки — курсорная пагинация по `id` (UUID v7 упорядочен по времени), фильтры по треку, году, статусу, номеру КИМ, теме, строке поиска.
- Ошибки — существующий конверт; CSRF — существующий middleware; все изменяющие запросы требуют токен.

Альтернатива: отдельный сервис админки. Отвергнута — противоречит модульному монолиту.

### 8. Аудит

- `admin.audit_log`: `id`, `actor_id`, `actor_role`, `action`, `entity`, `entity_id`, `before_json`, `after_json`, `ip`, `created_at`.
- `admin.Service` выполняет операцию через интерфейс `content`/`auth`, затем пишет аудит отдельной транзакцией.
- `before_json`/`after_json` не содержат паролей, токенов и секретов; для действий с пользователями сохраняются только роль и статус.
- Ошибка записи аудита логируется на уровне `error` и не откатывает уже применённое изменение; это осознанный компромисс.
- Просмотр аудита — только `admin`, с фильтрами по актору, действию, объекту и периоду.

Альтернатива: атомарный аудит в транзакции изменения через интерфейс-рекордер (как `notify.Enqueue` в этапе 1). Отвергнута на этом этапе: усложняет конструкторы `content` и порядок сборки в `main.go`, а цена потери записи при сбое БД мала. Зафиксировано в рисках; при требовании строгой гарантии — перейти на рекордер.

### 9. Проверка трека в учебных целях

- `profile` объявляет `ExamProvider` с методом проверки доступности трека по UUID.
- `content` реализует проверку: трек существует и опубликован.
- `profile.Service.SaveGoal` вызывает провайдер до записи; ошибка провайдера не маскируется под «трек не найден».
- Проверка выполняется в момент сохранения; последующая депубликация трека не инвалидирует уже сохранённую цель.

Альтернатива: денормализовать код трека в `profile`. Отвергнута — дублирование справочника и рассинхронизация.

### 10. SPA админки

- Vue 3 Composition API, Vite, Pico.css; TipTap v3 для условий, теории и критериев; KaTeX-узел для формул; highlight.js для подсветки кода.
- TipTap сериализует содержимое в Markdown, чтобы соответствовать ТЗ 10.5; HTML из редактора не сохраняется как источник истины.
- Сборка Vite кладётся в `web/admin/dist`; Go-бинарь встраивает каталог через `go:embed`. В репозитории хранится минимальный `index.html`-placeholder, чтобы `go build ./...` работал до `npm run build`; CI собирает SPA и проверяет отсутствие расхождений.
- `/admin` и `/admin/*` отдают SPA; `/api/admin/*` — JSON. Серверная проверка роли выполняется на каждом API-запросе, SPA-роутинг не является защитой.
- CSP расширяется `font-src 'self' data:` для шрифтов KaTeX; скрипты и стили остаются с `'self'`.

Альтернатива: серверный рендер админки на Templ. Отвергнута — ТЗ 5.13 и `AGENTS.md` требуют Vue SPA и TipTap.

### 11. Стартовый seed

- Seed создаёт три трека (`oge_math`, `ege_math_profile`, `ege_math_base`), учебный год, примерную структуру КИМ по ТЗ 10.1, несколько тем и теорию, демонстрационные задания и по одному варианту.
- Seed идемпотентен: повторный запуск не создаёт дубликатов (проверка по кодам и хешам).
- Полный объём ТЗ 10.2 — задача наполнения, а не кода; фиксируется как non-goal этапа.

Альтернатива: seed в миграции. Отвергнута — смешивает схему и данные, затрудняет откат и повторный запуск.

## Risks / Trade-offs

- [Аудит пишется после изменения и может не записаться при сбое БД] → Ошибка логируется на уровне `error`; изменение остаётся применённым. При требовании строгой гарантии перейти на рекордер в транзакции изменения.
- [Уникальный хеш условия блокирует легитимные одинаковые условия в разных номерах КИМ] → Дедупликация по условию является требованием FR-CONT-10; при необходимости различать задания используется `source_ref`, а не дублирование условия.
- [SPA-сборка добавляет Node в CI и placeholder в репозиторий] → Отдельная job сборки SPA; placeholder минимален и перезаписывается сборкой; Go-сборка не зависит от Node.
- [CSP расширяется под шрифты формул] → Добавляется только `font-src 'self' data:`; внешние CDN для шрифтов не используются.
- [Импорт без NLP требует ручного заполнения полей] → Осознанно: надёжность важнее автоматизации; AI-разбор — этап 7.
- [Версионирование копирует данные задания] → Объём истории ограничен числом правок; чтение активной версии не усложняется.
- [S3 недоступен] → Загрузка изображений возвращает `502 upstream_error`; редактирование текстового контента продолжает работать.
- [Генерация вариантов может не найти достаточно заданий] → Отказ без частичного сохранения и понятное сообщение методисту.
- [Проверка трека в `profile` создаёт зависимость `profile → content`] → Зависимость односторонняя и через интерфейс; граф зависимостей остаётся ациклическим.

## Долг, перенесённый на этап 5

На этапе 2 валидация `answer_spec` (`internal/content/service.go`) проверяет только поле `kind` по фиксированному списку (`number`, `interval`, `digits`, `text`, `choice`, `extended`); поля внутри `kind` не валидируются. Это осознанное упрощение: реестр стратегий проверки и per-kind схема полей — ядро модуля `grading` (этап 5, `stage-5-practice-autocheck`).

На этапе 5:

- набор допустимых `kind` и правила полей переносятся в реестр стратегий `grading`; `content` объявляет consumer-интерфейс валидатора;
- `answer_spec` валидируется по схеме своего `kind` (`accepted`, `tolerance`, `units`, `option_ids`, `ignore_yo` и т.д.);
- тест `TestValidateAnswerSpec` переносится/расширяется вместе с реестром.

До этапа 5 текущее поведение сохраняется; предметная нейтральность обеспечивается тем, что список `kind` не привязан к предмету.
