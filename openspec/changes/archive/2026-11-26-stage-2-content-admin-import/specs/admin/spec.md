## Purpose

Определяет административный контур платформы: серверный API для ведения контента и пользователей, разграничение прав методиста и администратора, журнал аудита действий и административный веб-интерфейс для работы без участия разработчика.

## ADDED Requirements

### Requirement: Доступ в административный контур

Система SHALL предоставлять административный контур только пользователям с ролью методиста или администратора. Любой запрос к административным ресурсам MUST проверять аутентификацию и роль на сервере. Методист MUST NOT изменять роли пользователей и MUST NOT получать доступ к платёжным данным.

#### Scenario: Доступ методиста

- **WHEN** методист обращается к административному ресурсу управления контентом
- **THEN** запрос выполняется в пределах прав методиста

#### Scenario: Доступ ученика

- **WHEN** ученик или родитель обращается к административному ресурсу
- **THEN** запрос отклоняется как запрещённый, а данные не раскрываются

#### Scenario: Неаутентифицированный запрос

- **WHEN** неаутентифицированный пользователь обращается к административному ресурсу
- **THEN** запрос отклоняется с требованием входа

#### Scenario: Методист меняет роли

- **WHEN** методист пытается изменить роль пользователя
- **THEN** действие отклоняется как запрещённое, а роль остаётся прежней

### Requirement: Управление контентом через API

Система SHALL предоставлять API для управления треками, учебными годами, номерами КИМ, темами, теорией, заданиями, вариантами, рубриками и шкалами. Списки MUST поддерживать фильтрацию и курсорную пагинацию. Все изменения MUST возвращать актуальное состояние объекта.

#### Scenario: Создание сущности контента

- **WHEN** методист создаёт сущность контента через API
- **THEN** сущность сохраняется и возвращается с присвоенным идентификатором

#### Scenario: Изменение сущности контента

- **WHEN** методист изменяет существующую сущность
- **THEN** изменения сохраняются, а ответ содержит обновлённое состояние

#### Scenario: Постраничный список

- **WHEN** методист запрашивает список с большим числом записей
- **THEN** возвращается страница с курсором для продолжения, без полной выгрузки

### Requirement: Импорт и публикация через админку

Система SHALL предоставлять административные операции импорта заданий и публикации. Импорт MUST создавать черновики и MUST NOT публиковать задания автоматически. Публикация MUST выполняться отдельным действием методиста или администратора.

#### Scenario: Импорт через административный интерфейс

- **WHEN** методист запускает импорт заданий
- **THEN** создаются черновики, а публикация не происходит

#### Scenario: Публикация после проверки

- **WHEN** методист публикует проверенное задание
- **THEN** задание становится опубликованным, а действие фиксируется в аудите

### Requirement: Рубрики и шкалы

Система SHALL предоставлять административные операции редактирования рубрик части 2 и таблиц перевода баллов. Изменения MUST проверяться на сервере до сохранения. Новая версия рубрики MUST NOT изменять уже сохранённые результаты проверок.

#### Scenario: Редактирование рубрики

- **WHEN** методист сохраняет изменённые критерии рубрики
- **THEN** создаётся новая версия, а прежние проверки сохраняют свои результаты

#### Scenario: Редактирование шкалы

- **WHEN** методист обновляет шкалу перевода учебного года
- **THEN** шкала сохраняется после успешной валидации диапазона

### Requirement: Управление пользователями и ролями

Система SHALL позволять администратору искать пользователей, блокировать и разблокировать учётные записи и изменять роли. Блокировка MUST немедленно прекращать доступ пользователя к защищённым ресурсам. Смена роли MUST вступать в силу при следующей проверке прав. Список пользователей MUST NOT раскрывать пароли, токены и лишние персональные данные.

#### Scenario: Блокировка пользователя

- **WHEN** администратор блокирует учётную запись
- **THEN** пользователь теряет доступ, а его активные сессии прекращают действовать

#### Scenario: Смена роли

- **WHEN** администратор изменяет роль пользователя
- **THEN** новая роль применяется при следующей проверке прав, а изменение фиксируется в аудите

#### Scenario: Поиск пользователей

- **WHEN** администратор ищет пользователей по адресу или идентификатору
- **THEN** возвращается ограниченный набор полей без секретов и лишних персональных данных

#### Scenario: Методист ищет пользователей

- **WHEN** методист пытается изменить статус или роль пользователя
- **THEN** действие отклоняется как запрещённое

### Requirement: Журнал аудита

Система SHALL записывать в журнал аудита все действия методиста и администратора. Запись MUST содержать актора, действие, объект, время и IP-адрес. Запись MUST NOT содержать пароли, токены и секреты. Просмотр журнала MUST быть доступен только администратору.

#### Scenario: Запись действия

- **WHEN** методист выполняет изменяющее действие над контентом
- **THEN** в журнале появляется запись с актором, действием, объектом, временем и IP

#### Scenario: Просмотр аудита администратором

- **WHEN** администратор запрашивает журнал с фильтрами
- **THEN** возвращаются записи, соответствующие фильтрам

#### Scenario: Просмотр аудита методистом

- **WHEN** методист запрашивает журнал аудита
- **THEN** запрос отклоняется как запрещённый

#### Scenario: Секреты в аудите

- **WHEN** выполняется действие, связанное с аутентификацией или токенами
- **THEN** в записи аудита отсутствуют пароли и токены

### Requirement: Валидация и безопасность входных данных

Система SHALL проверять все административные входные данные на сервере. Изменяющие запросы MUST требовать CSRF-токен. Пользовательский текст MUST санитизироваться по allowlist при рендере. Все запросы к данным MUST быть параметризованными. SPA MUST NOT считаться границей безопасности.

#### Scenario: Некорректные входные данные

- **WHEN** административный запрос содержит некорректные или отсутствующие обязательные поля
- **THEN** запрос отклоняется с ошибкой валидации по полям, а данные не сохраняются

#### Scenario: Запрос без CSRF-токена

- **WHEN** изменяющий административный запрос отправлен без действующего CSRF-токена
- **THEN** запрос отклоняется как запрещённый

#### Scenario: Небезопасный HTML

- **WHEN** в условии задания или теории присутствует потенциально небезопасный HTML
- **THEN** при рендере он удаляется или экранируется по allowlist

### Requirement: Административный веб-интерфейс

Система SHALL предоставлять административный веб-интерфейс для ведения контента. Интерфейс MUST поддерживать редактирование условий, теории и критериев с формулами и подсветкой синтаксиса. Все изменяющие запросы интерфейса MUST содержать CSRF-токен, а доступ MUST проверяться на сервере.

#### Scenario: Редактирование условия с формулой

- **WHEN** методист редактирует условие задания с формулой
- **THEN** формула отображается в редакторе и сохраняется в переносимом виде

#### Scenario: Доступ к интерфейсу без прав

- **WHEN** пользователь без служебной роли открывает административный интерфейс
- **THEN** интерфейс не предоставляет данные и действия, а серверные запросы отклоняются

#### Scenario: Изменяющий запрос из интерфейса

- **WHEN** методист сохраняет изменения из интерфейса
- **THEN** запрос отправляется с CSRF-токеном и сервер проверяет права
