## Context

См. `proposal.md` — Why. К началу этапа есть:

- модуль `content` с опубликованными треками, учебными годами, номерами КИМ, темами, теорией, заданиями (`status`, `is_public`), вариантами, рубриками и шкалами; чтение публичных заданий уже есть (`ListPublicTasks`, `GetTask`, `ListTaskAttachments`);
- `shared/markdown` (рендер и санитизация Markdown, проверка LaTeX), выдача изображений `/media/{key}`, `shared/render` с Templ-лейаутом для страниц авторизации;
- `notify` с outbox, шаблонами в БД и воркером; `auth` с сессиями, ролями, `Auth`/`RequireRole` и `Principal`;
- `httpserver` с request_id, recovery, логированием, лимитом тела, security headers, CSRF и rate limiter;
- миграции `000001`–`000007`, seed контента, CI и Makefile.

Ограничения, формирующие подход:

- `AGENTS.md`: модульный монолит, `Handler → Service → Repository`, pgx v5 и ручной SQL, транзакции только в Service, UUID v7, `context.Context` первым аргументом, `log/slog`, запрет `os.Getenv` вне config, интерфейс объявляет потребитель, сборка зависимостей только в `cmd/server/main.go`, только русский язык.
- Границы модулей: у каждого модуля своя схема; запрещены FK и JOIN между схемами; ссылки только по UUID; чтение чужого модуля только через интерфейс его сервиса. Внутри одной схемы JOIN допустим.
- ТЗ 6.6: межмодульные операции не выполняются в одной транзакции; согласованность через outbox или eventual consistency.
- ТЗ 5.1: в банке только `active` + `is_public`; задания платных пробников не раскрываются; демо использует отдельный пул публичных заданий.
- ТЗ 8.3: публичные маршруты заданы, но список неполный (нет `/hx/...` и служебных страниц).
- ТЗ 5.6 и 11.1–11.2: проверка короткого ответа строится на стратегиях по `answer_spec.kind`, нормализация общая.
- ТЗ 15.1–15.3: unit-тесты на весь функционал, интеграционные тесты с реальным PostgreSQL.

Конфликты требований и принятое решение:

| Конфликт | Решение |
|---|---|
| ТЗ 5.1 не задаёт колонки `public.articles`, `public.leads`, `public.seo_pages` | Колонки выводятся из назначения и ТЗ 5.1; `public.redirects` добавляется для SEO-алиасов, чтобы не хардкодить предметные пути |
| ТЗ 5.6 относит `grading` к этапу 5, но FR-PUB-03 требует проверку ответа уже на этапе 3 | На этапе 3 создаётся `internal/grading` с минимальным набором стратегий (`number`, `text`, `digits`, `interval`); этап 5 расширяет реестр, добавляет per-kind валидацию `answer_spec` и интеграцию с `learning`, а не создаёт библиотеку заново |
| ТЗ 5.1 требует скрывать задания платных пробников «если включён режим защиты контента», но флага режима нет | Отдельный флаг не вводится: задания, входящие в опубликованный пробник, по умолчанию исключаются из банка и демо. Это трактовка ограничения; отдельный флаг — открытый вопрос |
| ТЗ 5.13 не включает статьи и SEO-страницы в админку, но этап 3 требует статьи | На этапе 3 статьи и SEO-страницы наполняются seed; админский CRUD — non-goal и отдельный будущий change |
| `render.Layout` рассчитан на страницы авторизации и не содержит SEO-метаданных | Создаётся отдельный публичный layout в `publicsite`; `render.Layout` не меняется |
| CSP запрещает сторонние скрипты, а для формул нужен KaTeX | CSP расширяется только для `https://cdn.jsdelivr.net` в `script-src` и `font-src`; HTMX и `public.js` хостятся самостоятельно. Self-host KaTeX — открытый вопрос |

## Goals / Non-Goals

**Goals:**

- Дать публичный контур, полностью работающий от опубликованного контента `content` без правок учебного цикла.
- Сделать публичные страницы SEO-пригодными: канонические адреса, метаданные, Open Graph, хлебные крошки, sitemap, robots.
- Дать проверку короткого ответа без сохранения истории и без регистрации, переиспользуемую на этапе 5.
- Сохранить границы модулей: `publicsite` читает `content`/`auth` только через интерфейсы и не обращается к их таблицам.
- Уложиться в существующие компоненты: Templ, HTMX, Pico.css, `shared/markdown`, `notify`-outbox, CSRF, rate limit.

**Non-Goals:**

- Регистрация, вход, личный кабинет и полный отчёт демо для зарегистрированных (этапы 1–2 и 4).
- Проверка части 2, AI-черновики, очередь методиста и апелляции (этап 7).
- Платежи, подписки и ограничение доступа к платному контенту (этап 9).
- In-app уведомления и недельные отчёты (этапы 8, 10).
- Админский CRUD статей, SEO-страниц и редиректов; управление ими через seed и будущий change.
- Полнотекстовый поиск, NLP-разбор и AI-генерация контента.
- Отдельный режим защиты контента сверх исключения заданий опубликованных пробников.
- Self-host KaTeX и переход на распределённый кэш.

## Decisions

### 1. Модули и границы

```
internal/
  publicsite/
    handler.go      — публичные HTTP-маршруты, HTML-ошибки, HTMX-фрагменты
    service.go      — сценарии: лендинг, банк, проверка, демо, статьи, лиды, sitemap, редиректы
    repository.go   — SQL по схеме public
    entity.go       — Article, Lead, SEOPage, Redirect
    dto.go          — входные данные форм и фильтров
    cache.go        — in-memory TTL-кэш HTML
    demo.go         — подписанный cookie демо-диагностики
    views.templ     — layout, лендинг, банк, карточка, демо, статьи, лид-форма, ошибки
    assets/         — htmx.min.js, public.js (go:embed)
  grading/
    grading.go      — Check(spec, answer) и общий результат
    normalize.go    — общая нормализация
    number.go, text.go, digits.go, interval.go — стратегии
```

`publicsite` объявляет интерфейсы потребителя:

- `ContentProvider` — чтение опубликованных треков, учебных годов, номеров КИМ, тем, публичных заданий, вложений и демо-пула. Методы возвращают типы `content`, как это уже делает `admin`.
- `RecipientProvider` — список email активных администраторов.
- `Notifier` — постановка письма в outbox (`Enqueue(ctx, q, notify.Message)`), как в `auth`.

`grading` — чистая библиотека без БД, зависимостей от Gin и `content`. `publicsite` вызывает её из Service.

Альтернатива: `publicsite` обращается к таблицам `content` напрямую. Отвергнута — нарушает границы модулей и дублирует правила публикации.

Альтернатива: отдельный сервис публичного контура. Отвергнута — противоречит модульному монолиту.

### 2. Схема `public`

```
public.articles    id, slug UNIQUE, title, excerpt, content_md, status, published_at, created_at, updated_at
public.leads       id, name, contact, comment, source, status, created_at
public.seo_pages   id, path UNIQUE, title, description, og_title, og_description, og_image,
                   canonical_path, noindex, created_at, updated_at
public.redirects   id, from_path UNIQUE, to_path, status_code, created_at
```

- `articles.status` — `draft`/`published`/`archived`; публично доступны только `published` с непустым `published_at`.
- `leads` не хранит IP и user-agent: минимизация ПДн (SEC-PD-01). Антиспам опирается на honeypot, rate limit и валидацию.
- `seo_pages` — источник метаданных для статических страниц (`/`, `/bank`, `/diagnostics/demo`, `/articles`, `/tracks/{code}`); для статьи метаданные берутся из её полей с необязательным переопределением по пути.
- `redirects` — данные SEO-алиасов (`/oge` → `/tracks/oge_math` и т.п.); `to_path` обязан начинаться с `/` и не с `//`, чтобы исключить open redirect.
- Внешних ключей между схемами нет; внутри `public` FK не требуются, кроме логических связей по slug/path.
- Индексы: `articles(status, published_at DESC)`, `seo_pages(path)`, `redirects(from_path)`.

Альтернатива: хранить статьи и SEO в `content`. Отвергнута — `content` владеет учебным контентом, а публичные статьи и заявки — другой жизненный цикл.

Альтернатива: хардкодить алиасы в роутере. Отвергнута — FR-PUB-01 прямо запрещает предметные маршруты.

### 3. Публичные маршруты и рендеринг

- Полные страницы: `/`, `/tracks/{examCode}`, `/bank`, `/bank/{taskId}`, `/articles`, `/articles/{slug}`, `/diagnostics/demo`.
- HTMX-фрагменты: `/hx/bank`, `/hx/leads`, `/hx/demo/result`; изменяющие действия — `POST /bank/{taskId}/check`, `POST /diagnostics/demo/check`, `POST /leads`.
- SEO-алиасы: `GET /:alias` регистрируется последним и ищет путь в `public.redirects`; статические маршруты Gin имеют приоритет, поэтому известные страницы не перехватываются.
- `GET /sitemap.xml` и `GET /robots.txt` — отдельные обработчики с корректными типами содержимого.
- HTML-ошибки публичных страниц рендерятся публичным layout с кодом `404`/`422`/`500`; JSON-конверт остаётся для API.
- HTMX и `public.js` отдаются с `/static/public/*` из `go:embed` с долгим `Cache-Control`; Pico.css и KaTeX — с CDN, как уже принято для Pico.
- `public.js` вызывает `renderMathInElement` по `DOMContentLoaded`; inline-скрипты не используются, чтобы не ослаблять CSP.

Альтернатива: только полные перезагрузки страниц без HTMX. Отвергнута — `AGENTS.md` и ТЗ 8.1 требуют HTMX для фрагментов.

### 4. Лендинги треков

- `GET /tracks/{examCode}`: трек по коду, только `published`; иначе `404`.
- Последний опубликованный учебный год, номера КИМ и темы читаются через `ContentProvider`. Если опубликованного года нет, страница показывает описание и CTA без структуры.
- SEO-метаданные: `seo_pages` по пути `/tracks/{code}`, иначе заголовок трека.
- CTA: регистрация, демо-диагностика, открытый банк.
- Лендинг кэшируется на 60 секунд; форма лида рендерится с CSRF-плейсхолдером (см. §8).

Альтернатива: генерировать лендинги статически при публикации. Отвергнута — усложняет инвалидацию и не даёт выигрыша при 60-секундном кэше.

### 5. Открытый банк и проверка ответа

- `ContentProvider.ListPublicTasks` получает фильтры: трек, учебный год, номер КИМ, тема, курсор, лимит, набор допустимых `answer_spec.kind`, флаг исключения заданий опубликованных пробников.
- SQL `content` фильтрует `status='published'`, `is_public=true`, `answer_spec->>'kind' = ANY(...)` и `NOT EXISTS` по `variant_tasks`/`variants` (`kind='mock'`, `status='published'`). Это JOIN внутри схемы `content`, границы не нарушены.
- Курсорная пагинация по `id` (UUID v7), лимит по умолчанию 20, максимум 50.
- Карточка задания не отдаёт `answer_display` и `answer_spec` до проверки; изображения — через `/media/{key}`.
- `POST /bank/{taskId}/check`:
  - загружает задание и проверяет, что оно опубликовано, публично и его `kind` поддерживается;
  - вызывает `grading.Check`;
  - возвращает результат «верно/неверно», правильный ответ и краткое пояснение;
  - не пишет в БД и не создаёт сессию;
  - при неизвестном/неподдерживаемом `kind` — `422`;
  - защищён CSRF и rate limit.
- «Краткое объяснение» на этапе 3 — правильный ответ из `answer_display` и название темы. Отдельное поле объяснения — открытый вопрос.

Альтернатива: собственная нормализация в `publicsite`. Отвергнута — дублирует `grading` и разойдётся с этапом 5.

### 6. Демо-диагностика

- `GET /diagnostics/demo` без параметра показывает выбор опубликованного трека; с `?exam={code}` запускает демо.
- Пул: `ListDemoTasks` — публичные, опубликованные, автоматически проверяемые задания, исключая задания опубликованных пробников; не более одного задания на номер КИМ, случайный порядок, 5–7 заданий. При нехватке — понятное пустое состояние.
- Состояние: подписанный HMAC-SHA256 cookie `demo_session` с `exam_year_id`, списком `task_id`, временем выпуска и nonce. Секрет — `SESSION_SECRET`; TTL 30 минут; `HttpOnly`, `Secure` в production, `SameSite=Lax`. В БД ничего не пишется.
- `POST /diagnostics/demo/check` проверяет подпись и срок, загружает задания, проверяет ответы, показывает итог и разбивку по темам, очищает cookie. Истёкшая или изменённая подпись — `422` с понятным сообщением.
- Результат не создаёт учебную сессию; CTA ведёт на регистрацию для полного отчёта.
- Страницы демо не кэшируются.

Альтернатива: хранить демо-сессию в БД. Отвергнута — лишние записи и очистка; подписанного cookie достаточно, история не нужна.

### 7. Статьи и SEO

- `GET /articles` — опубликованные статьи, `published_at DESC`, курсорная пагинация.
- `GET /articles/{slug}` — статья по slug, только `published`; Markdown рендерится и санитизируется `shared/markdown`.
- Метаданные: title/excerpt статьи, canonical `/articles/{slug}`, Open Graph; необязательное переопределение из `seo_pages`.
- Хлебные крошки: «Главная → Статьи → Заголовок».
- `GET /sitemap.xml`: `/`, опубликованные треки, `/bank`, `/diagnostics/demo`, `/articles`, опубликованные статьи; `lastmod` из `updated_at`/`published_at`; черновики и личные страницы исключены. XML формируется `encoding/xml`.
- `GET /robots.txt`: запрет `/admin`, `/account`, `/login`, `/register`, `/password`, `/api/`, `/hx/`; ссылка `Sitemap: {APP_BASE_URL}/sitemap.xml`.

Альтернатива: генерировать sitemap из БД на лету без кэша. Принято; страница дешёвая, кэш не обязателен.

### 8. Кэширование публичных страниц

- `publicsite.cache` — in-memory `map[string]entry` с `sync.Mutex`, TTL 60 секунд, верхняя граница числа записей (например, 1000) с удалением истёкших и самых старых.
- Кэшируются только успешные `200 text/html` ответы анонимных посетителей. Ключ — `URL.RequestURI()` с отсортированными query-параметрами.
- Запрос с cookie сессии (`auth.SessionTokenFromRequest`) кэш не использует; страница рендерится персонально.
- Ответы с `Cache-Control: no-store` (демо, результаты проверок, формы после отправки) не кэшируются.
- CSRF на закэшированных страницах: шаблон рендерит плейсхолдер `__CSRF__`; helper `renderCached` при выдаче заменяет его на действующий токен из CSRF-контекста. При промахе страница рендерится с плейсхолдером, сохраняется в кэш, затем токен подставляется в ответ. Так форма работает для любого посетителя.
- Хендлеры, которые не используют `renderCached`, рендерят реальный токен и не кэшируются.
- Инвалидации нет: изменения контента видны в течение 60 секунд. Это соответствует FR-PUB-08.

Альтернатива: общий middleware-кэш с обёрткой `gin.ResponseWriter`. Отвергнута — сложнее в отладке и требует поддержки `Flush`/`Hijack`; явный helper проще и покрывает только нужные страницы.

Альтернатива: кэшировать вместе с CSRF-токеном первого посетителя. Отвергнута — double-submit сравнивает cookie и поле, токен первого посетителя не совпадёт с cookie другого.

### 9. Лид-форма и уведомление

- Поля: `name` (2–100), `contact` (3–200, email или телефон), `comment` (до 2000), скрытое `website` (honeypot), `source` (до 100, путь/метка страницы).
- Валидация в Service; при honeypot или превышении rate limit — нейтральный успешный ответ без записи.
- Заявка сохраняется в `public.leads` в транзакции Service. IP и user-agent не сохраняются.
- После коммита Service получает email активных администраторов через `RecipientProvider` и для каждого ставит письмо `lead_notification` в outbox через `Notifier.Enqueue(ctx, s.db, msg)`; `dedup_key = lead:{leadID}:{adminID}`.
- Ошибка постановки письма логируется на уровне `error` без имени, контакта и комментария; заявка остаётся сохранённой. Это осознанное отступление от «одна транзакция» ради требования не терять заявку.
- Шаблон `lead_notification` добавляется миграцией; тело содержит имя, контакт, комментарий и источник. Outbox хранит payload с ПДн, но логи и `last_error` их не содержат; срок хранения outbox — 90 дней по ТЗ 7.9.
- Если активных администраторов нет, заявка сохраняется, а отсутствие получателей логируется предупреждением.

Альтернатива: писать заявку и outbox в одной транзакции. Отвергнута — при ошибке enqueue пришлось бы откатывать заявку, что нарушает «не терять сохранённую заявку».

Альтернатива: отправлять письмо синхронно. Отвергнута — блокирует запрос и дублирует механизм `notify`.

### 10. Проверка коротких ответов (`grading`)

- `Check(spec json.RawMessage, answer string) (Result, error)`; `Result` содержит `Correct`, `Reason` (`matched`, `mismatch`, `partial`, `needs_review`, `unsupported`), нормализованный ответ и эталон для отображения.
- Общая нормализация: trim, унификация минуса, `ё`/`е` и регистр по настройкам `kind`.
- `number`: запятая/точка, пробелы, разделители тысяч, дроби `a/b`, абсолютный/относительный допуск, единицы.
- `text`: `accepted`, `case_sensitive`, `ignore_yo`, `ignore_hyphen`, повторные пробелы.
- `digits`: `accepted`, `length`, `order_matters`.
- `interval`: разбор концов и скобок, сравнение множеств без учёта порядка; при неудачном разборе — нормализованное строковое сравнение.
- `choice` и `extended` возвращают `unsupported`; публичный контур их не предлагает.
- Неизвестные поля `answer_spec` игнорируются; per-kind валидация схемы — этап 5. Это сохраняет совместимость с текущей валидацией `content`, которая проверяет только `kind`.

Альтернатива: реализовать полный реестр сразу. Отвергнута — расширяет scope этапа и дублирует этап 5.

### 11. Безопасность

- Публично показывается только опубликованный контент; проверка статуса выполняется в Service, а не только в шаблоне.
- Markdown санитизируется `shared/markdown`; пользовательские строки экранируются Templ.
- Все изменяющие публичные запросы проходят глобальный CSRF-middleware; формы содержат токен.
- Rate limit на `POST /leads`, `POST /bank/{id}/check`, `POST /diagnostics/demo/check` и поиск `/bank` — существующий `RATE_LIMIT_API_PER_MIN` по IP.
- Логи не содержат ответы учеников, имена, контакты и комментарии; `notify` уже логирует без payload.
- `robots.txt` и `noindex` закрывают личные и административные разделы; `X-Robots-Tag` не требуется, достаточно метатега и robots.
- CSP: добавляются `https://cdn.jsdelivr.net` в `script-src` и `font-src` для KaTeX. HTMX и `public.js` — только `'self'`. Внешние скрипты ограничены одним источником; SRI для KaTeX — желательное улучшение.

Альтернатива: разрешить `'unsafe-inline'` для скриптов. Отвергнута — ослабляет CSP; `public.js` вынесен в файл.

## Risks / Trade-offs

- [KaTeX с CDN и расширение CSP] → Ограничиваемся одним доверенным CDN, используем SRI при возможности; self-host KaTeX зафиксирован как открытый вопрос.
- [Закэшированная страница с CSRF-плейсхолдером может сломать форму, если хендлер забыл подстановку] → Все кэшируемые формы используют общий helper; unit-тест проверяет наличие плейсхолдера и подстановку токена.
- [Кэш устаревает до 60 секунд] → Принято по FR-PUB-08; изменения контента появляются в течение минуты.
- [In-memory кэш не разделяется между инстансами] → Для MVP один инстанс; распределённый кэш — открытый вопрос при масштабировании.
- [Исключение заданий опубликованных пробников может опустошить банк] → Seed оставляет достаточно заданий вне пробника; пустое состояние объясняет причину; тест проверяет непустой банк после seed.
- [Демо-cookie можно воспроизвести до истечения TTL] → Подпись и TTL; результат не сохраняется, поэтому повтор не влияет на данные. Cookie очищается после результата.
- [Ошибка enqueue уведомления о лиде] → Заявка сохранена, ошибка логируется без ПДн; повторная отправка — будущее улучшение.
- [ПДн в payload outbox] → Необходимы для письма; логи и `last_error` очищены; срок хранения 90 дней по ТЗ.
- [Нет админского CRUD статей и SEO] → Наполнение через seed; ограничение зафиксировано как non-goal и открытый вопрос.
- [Catch-all `/:alias` может перехватить будущий маршрут] → Регистрируется последним; статические маршруты имеют приоритет; тест проверяет известные пути.
- [Open redirect через `redirects`] → `to_path` обязан начинаться с `/` и не с `//`; проверка в Service и тест.
