## Context

См. `proposal.md` — Why. Текущее состояние, важное для реализации:

- `internal/grading` уже умеет `number`, `text`, `digits`, `interval`, но не имеет `choice`, per-kind валидации и единого перечня типов.
- `internal/learning` содержит диагностику, снимки заданий, ответы, освоение тем и номеров КИМ, недельный план. `learning.sessions.kind` допускает `diagnostic`, `practice`, `mock`, но не `review`; поля `interval_days`, `ease`, `next_review_at` есть в схеме, но не обновляются.
- `content.task_options` существует только как таблица: нет entity, repository, service, импорта и административного API.
- `publicsite` использует `grading.Supports` и сейчас считает `choice` неподдерживаемым; его тесты это фиксируют.
- Ограничения `AGENTS.md`: границы модулей, отсутствие FK и JOIN между схемами, транзакции только в Service, UUID v7, ручной SQL, pgx v5, отсутствие ORM.

Поток этапа 5:

```
тема / номер КИМ / пункт плана
              |
              v
      сессия practice или review
              |
              v
  ответ -> grading.Check -> answers
              |
              v
  завершение -> результат -> mastery -> interval -> plan item done
```

## Goals / Non-Goals

**Goals:**

- Замкнуть цикл «практика → проверка → освоение → повторение ошибок» без новых таблиц `learning`.
- Сделать `grading` единственным источником истины о типах ответа и их валидации.
- Поддержать `choice` end-to-end, включая авторинг, снимок и проверку.
- Сохранить предметную нейтральность: выбор заданий и проверка не ветвятся по предмету или коду трека.
- Переиспользовать существующие сессии, снимки, ответы, результат и mastery вместо параллельной реализации.

**Non-Goals:**

- Пробники, дедлайны, таймер, шкалы (этап 6).
- Часть 2, AI, рубрики, очередь методиста (этап 7); `FR-GRADE-09` не реализуется.
- Публичный рендер `choice` в банке и демо (отдельное изменение `public-site`).
- Freemium-лимиты (`FR-LEARN-12`) и проверка прав перед стартом (этап 9).
- Новые таблицы и JOIN между схемами.

## Decisions

### D1. Реестр `grading` как таблица стратегий, без интерфейсов

`grading` получает внутренний реестр: `kind -> {check, validate, public}`. Публичный API пакета:

- `Check(raw, answer) (Result, error)` — единая проверка;
- `Validate(raw) error` — per-kind валидация;
- `Kinds() []string` — все типы, для которых есть валидация `answer_spec` (включая `extended`);
- `CheckableKinds() []string` — типы с автоматической проверкой короткого ответа (`number`, `text`, `digits`, `interval`, `choice`);
- `PublicKinds() []string` — типы, доступные публичному контуру (`number`, `text`, `digits`, `interval`);
- `Supports(kind) bool`, `SupportsPublic(kind) bool`.

Альтернативы: интерфейс стратегии на каждый тип (лишняя абстракция), JSON Schema библиотека (новая зависимость ради одной функции). Выбран простой реестр: добавление типа — новая функция и запись в таблицу.

### D2. Валидация `answer_spec` живёт в `grading`, `content` её вызывает

`content` перестаёт хранить список `kind` и вызывает `grading.Validate`. `learning` получает типы через `grading.CheckableKinds`, `publicsite` и демо-диагностика `content` — через `grading.PublicKinds`. Это убирает три расходящихся списка и гарантирует, что новый тип не появится в одном месте и не появится в другом. `extended` остаётся валидируемым для части 2, но не входит в `CheckableKinds` и `PublicKinds`.

Для `choice` валидация дополнительно проверяет, что каждый `option_ids` существует среди вариантов задания и что набор правильных вариантов не пуст. Проверка существования вариантов выполняется в Service `content`, потому что требует чтения вариантов задания; `grading` проверяет только форму `answer_spec`.

### D3. `choice` реализуется через `content.task_options`, публичный банк остаётся на коротких ответах

Канонический формат:

```json
{"kind": "choice", "option_ids": ["uuid-1", "uuid-2"]}
```

`option_ids` — правильный набор. Ответ ученика — один или несколько идентификаторов вариантов; сравнение идёт как множество без учёта порядка. `is_correct` в `task_options` хранится для авторинга и проверки согласованности, но истиной при проверке считается `option_ids`.

Идентификаторы вариантов MUST быть известны до сохранения `answer_spec`. Поэтому:

- административный SPA генерирует UUID v7 для новых вариантов;
- импорт `choice` требует явные идентификаторы вариантов;
- seed-данные используют фиксированные UUID.

Снимок задания содержит варианты без признака правильности:

```json
{"options": [{"id": "uuid", "content_md": "..."}]}
```

`publicsite` продолжает фильтровать задания через `grading.SupportsPublic`; `choice` туда не входит. Это сохраняет поведение и тесты публичного контура и не расширяет этап 5 на `public-site`.

Альтернативы: хранить варианты внутри `answer_spec` (нарушает FR-GRADE-13), включить `choice` только в реестр без UI (мёртвая функциональность), добавить рендер `choice` в публичный банк (расширение scope).

### D4. Состав практики

- Ручной запуск по теме или номеру КИМ: целевое количество 10 заданий; если доступно меньше 10, используются все доступные, но не меньше одного.
- Запуск из пункта плана: количество берётся из `plan_items.task_count`, ограничивается 20.
- Только `published + is_public + supported kind`, кроме заданий опубликованных пробников.
- Порядок заданий перемешивается тем же способом, что и в `content`; для тестов внедряется детерминированный shuffler.
- Жёсткого таймера нет: `deadline_at` остаётся `NULL`.
- Снимок задания и вариантов фиксируется при старте; правки контента не меняют сессию.

Альтернативы: всегда 10 заданий из плана (может превысить недельную нагрузку), всегда 20 (слишком долго), брать задания без перемешивания (повторяемость).

### D5. Состав работы над ошибками

Кандидаты:

1. Темы, у которых `next_review_at <= now`.
2. Ранее неверно решённые задания пользователя, которые всё ещё опубликованы, публичны и поддерживают автоматическую проверку.

Приоритет: сначала должные темы, затем неверные задания. Дубликаты заданий удаляются. Целевой размер — 10 заданий, максимум 20. Если кандидатов нет — пустое состояние с переходом к практике или диагностике.

Запросы к `learning` и `content` раздельные: `learning` читает свои ответы и mastery, затем `content` отдаёт актуальные задания по идентификаторам или фильтрам. JOIN между схемами не используется.

### D6. Интервальное повторение считается по теме за сессию

`interval_days`, `ease`, `next_review_at` обновляются один раз на тему за завершённую сессию. Успех темы — отсутствие неверных ответов по этой теме в сессии. Это предотвращает многократное умножение интервала при нескольких заданиях одной темы в одной сессии.

Правила:

```
success: interval = min(interval * ease, 60); ease = min(ease + 0.1, 2.5)
failure: interval = 1;                      ease = max(ease - 0.2, 1.3)
initial: interval = 1; ease = 2.0
next_review_at = last_practiced_at + interval дней
```

Обновление выполняется в той же транзакции, что и результат сессии и mastery.

### D7. Переиспользование существующего жизненного цикла сессии

`SaveAnswer`, `SessionView`, `CompleteSession`, `Result` уже работают с любой сессией и снимком. Этап 5 добавляет:

- создание сессий `practice` и `review`;
- проверку `kind` при открытии kind-специфичного маршрута;
- обновление интервалов и завершение пункта плана в `CompleteSession`;
- отображение вариантов `choice` в экране сессии.

Отдельная параллельная реализация сессий не создаётся.

### D8. Миграция `000011_learning_practice`

UP:

```sql
ALTER TABLE learning.sessions DROP CONSTRAINT sessions_kind_check;
ALTER TABLE learning.sessions
    ADD CONSTRAINT sessions_kind_check
    CHECK (kind IN ('diagnostic', 'practice', 'review', 'mock'));

ALTER TABLE learning.sessions
    ADD COLUMN plan_item_id uuid REFERENCES learning.plan_items (id) ON DELETE SET NULL;

CREATE INDEX sessions_plan_item_idx ON learning.sessions (plan_item_id);
```

DOWN:

```sql
DROP INDEX IF EXISTS learning.sessions_plan_item_idx;
ALTER TABLE learning.sessions DROP COLUMN IF EXISTS plan_item_id;
ALTER TABLE learning.sessions DROP CONSTRAINT sessions_kind_check;
ALTER TABLE learning.sessions
    ADD CONSTRAINT sessions_kind_check
    CHECK (kind IN ('diagnostic', 'practice', 'mock'));
```

`plan_item_id` — FK внутри одной схемы `learning`, что разрешено. `mock` сохраняется, чтобы не менять планы этапа 6. DOWN не удаляет данные: если в базе есть сессии `review`, откат ограничения завершится ошибкой; это документируется, а перед откатом нужно удалить или преобразовать такие сессии.

### D9. Маршруты и интерфейс

HTML:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/app/practice` | выбор темы/номера КИМ и старт |
| POST | `/app/practice` | создать практику |
| GET | `/app/practice/:id` | прохождение |
| POST | `/app/practice/:id/items/:itemId` | сохранить ответ |
| POST | `/app/practice/:id/submit` | завершить |
| GET | `/app/practice/:id/result` | результат |
| GET | `/app/review` | старт работы над ошибками |
| POST | `/app/review` | создать сессию повторения |
| GET | `/app/review/:id` | прохождение |
| POST | `/app/review/:id/items/:itemId` | сохранить ответ |
| POST | `/app/review/:id/submit` | завершить |
| GET | `/app/review/:id/result` | результат |

JSON: `POST /api/sessions` с `kind` (`practice` или `review`) и фильтрами `topic_id`, `kim_number_id`, `plan_item_id`. Существующий `POST /api/diagnostics` сохраняется как совместимый маршрут.

Экраны используют компоненты `internal/shared/render/ui`, состояния загрузки/пусто/ошибка/недоступно/успех/ошибка валидации, видимый фокус и тач-цели не менее 44×44 px. Варианты `choice` рендерятся как radio/checkbox с текстом; правильность не раскрывается до отправки.

### D10. Завершение пункта плана

Если сессия создана из пункта плана, `plan_item_id` сохраняется в `sessions`. При успешном завершении сессии пункт отмечается выполненным в той же транзакции. Незавершённая сессия пункт не меняет. Повторное завершение идемпотентно.

### D11. Валидация и безопасность

- Все входные параметры проверяются в Handler/Service.
- Владелец сессии проверяется по `user_id`; чужая сессия даёт `forbidden` без раскрытия данных.
- CSRF обязателен для всех изменяющих HTML- и JSON-запросов.
- `answer_spec` и `task_options` не раскрываются до отправки ответа.
- `choice` не попадает в публичный банк; `PublicKinds` — единственный фильтр публичного контура.
- Ошибки оборачиваются с контекстом; логирование без персональных данных.

### D12. Тестирование и границы

- Unit-тесты `grading`: все типы, границы, допуски, единицы, `choice`, причины, валидация.
- Unit-тесты `learning`: состав практики, состав повторения, интервалы, идемпотентность завершения.
- Интеграционные тесты с PostgreSQL: старт практики по теме/КИМ/плану, сохранение ответов, завершение, mastery, interval, plan item, review.
- Проверка `go list -deps ./internal/grading` — без `learning`, `content` и БД.
- Проверка, что `publicsite` по-прежнему отклоняет `choice`.
- Миграция `up → down 1 → up` на чистой базе.

## Risks / Trade-offs

- **Сложность авторинга `choice`** → явные UUID вариантов, валидация, seed-пример, редактор в SPA.
- **Откат миграции при наличии `review`-сессий** → документированный порядок очистки; DOWN не удаляет данные автоматически.
- **Неоднозначность интервалов** → правило «успех темы = нет неверных ответов за сессию», покрытое unit-тестами.
- **Регрессия публичного банка** → `PublicKinds` и существующие тесты на неподдерживаемый `choice`.
- **Старые снимки без вариантов** → `options` с `omitempty`, чтение отсутствующего поля не ошибка.
- **Повторяемость заданий практики** → shuffler и исключение повторов в сессии.
- **Дублирование HTML-маршрутов practice/review** → общие handler-функции с проверкой `kind`; отдельные маршруты нужны для навигации и понятных URL.

## Migration Plan

1. Добавить миграцию `000011_learning_practice` (UP/DOWN).
2. Выполнить `up`, проверить `down 1` и повторный `up` на чистой базе.
3. Задеплоить код с новыми стратегиями и маршрутами; старые сессии и снимки продолжают читаться.
4. При откате: сначала удалить/преобразовать сессии `review`, затем `down 1`; иначе ограничение `sessions_kind_check` не восстановится.

- Нужен ли отдельный экран истории практик и повторений? Сейчас история доступна через план и результаты; отдельный экран — этап 8.
