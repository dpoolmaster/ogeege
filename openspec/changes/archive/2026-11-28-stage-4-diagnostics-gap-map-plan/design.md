## Context

См. `proposal.md` — Why. К началу этапа есть:

- `content` с опубликованными треками, учебными годами, номерами КИМ, темами, связями `kim_topics`, публичными заданиями (`status`, `is_public`), вариантами и снимком активной версии задания; чтение через `ListPublishedExams`, `GetExamByCode`, `GetLatestPublishedExamYear`, `ListKimNumbers`, `ListKimTopics`, `ListTopics`, `ListPublicTasks`, `GetTask`, `ListTaskAttachments`.
- `profile` с учебной целью (`StudyGoal`: трек, дата экзамена, целевой балл, недельное время) и историей целей; `SaveGoal` проверяет опубликованность трека и дату.
- `auth` с серверными сессиями, `AuthPage` для HTML и `Auth` для JSON, проверкой ролей и `CurrentUser`.
- `internal/grading` — чистая библиотека без БД; `Check` и `Supports` уже покрывают `number`, `text`, `digits`, `interval`, а `choice`/`extended` помечены как неподдерживаемые.
- `shared/render/ui` с `AppShell`, `TodayScreen`, `GapHeatmap`, `Card`, `Field`, `Button`, `EmptyState`, `ResultPanel`, токенами `--v-*`.
- `httpserver` с CSRF, rate limit, security headers, request_id и логированием.
- Миграции `000001`–`000009`; схема `learning` создана в `000001`, но таблиц в ней нет.
- `cmd/server/main.go` — единственное место сборки зависимостей.

Ограничения:

- `AGENTS.md`: модульный монолит, `Handler → Service → Repository`, pgx v5 и ручной SQL, транзакции только в Service, UUID v7, `context.Context` первым аргументом, `log/slog`, интерфейс объявляет потребитель, сборка только в `cmd/server/main.go`, только русский язык.
- Границы модулей: своя схема, нет FK и JOIN между схемами, ссылки только по UUID, чтение чужого модуля только через интерфейс.
- ТЗ 6.6: межмодульные операции не выполняются в одной транзакции; согласованность через повтор или eventual consistency.
- ТЗ 5.5 задаёт таблицы `study_plans`, `plan_weeks`, `plan_items`, `sessions`, `session_items`, `answers`, `topic_mastery`, `kim_mastery`, `session_results`, но ТЗ 7.4 перечисляет только `sessions`, `session_items`, `answers`, `topic_mastery`.
- ТЗ 4.2 одновременно требует покрыть все номера КИМ и уложиться в 45 минут.
- ТЗ 4.2 шаг 5 упоминает AI-рекомендации, но AI-контур — этап 7.

## Goals / Non-Goals

**Goals:**

- Дать ученику персональный маршрут от учебной цели до недельного плана, работающий только от опубликованного контента.
- Сделать диагностику воспроизводимой и объяснимой: покрытие номеров КИМ, снимок задания, причина результата.
- Сохранить границы модулей: `learning` читает `profile` и `content` только через объявленные им интерфейсы, `grading` импортирует как библиотеку.
- Переиспользовать дизайн-систему и не вводить новых визуальных паттернов.
- Оставить точки расширения для этапов 5–8 без изменения схемы: практика, пробники, шкалы, прогноз.

**Non-Goals:**

- Практика, работа над ошибками, интервальное повторение и полный реестр `grading` — этап 5.
- Пробники, жёсткий таймер, шкалы перевода и оценка — этап 6.
- AI-рекомендации, проверка части 2, очередь методиста и апелляции — этап 7.
- Статистика прогресса, прогноз балла и кабинет родителя — этап 8.
- Freemium-лимиты и платные сессии — этап 9.
- Перенос результата анонимной демо-диагностики в зарегистрированный отчёт — открытый вопрос; на этапе 4 полный отчёт относится к зарегистрированной диагностике.
- Полнотекстовый поиск, админский CRUD планов, тёмная тема.

## Decisions

### 1. Модуль и границы

```
internal/learning/
  handler.go      — HTML кабинета и JSON учебного цикла, CSRF, ошибки
  service.go      — учебная цель, диагностика, освоение, карта, план
  repository.go   — SQL схемы learning
  entity.go       — Plan, Week, Item, Session, SessionItem, Answer, Mastery, Result
  dto.go          — входные данные форм и JSON
  views.templ     — экраны кабинета на компонентах ui
```

`learning` объявляет интерфейсы потребителя:

- `GoalProvider` — текущая учебная цель и сохранение цели; реализует `profile.Service`.
- `ContentProvider` — опубликованные треки, годы, номера КИМ, темы, связи `kim_topics`, публичные задания и вложения; реализует `content.Service`.
- `TxManager` — транзакции; реализует существующий менеджер.

`internal/grading` импортируется напрямую: это библиотека без схемы и без обратных зависимостей. Учебный цикл не ветвится по предмету или коду трека.

Альтернатива: `learning` обращается к таблицам `content`/`profile` напрямую. Отвергнута — нарушает границы модулей.

Альтернатива: `learning` дублирует нормализацию ответов. Отвергнута — `grading` уже создан на этапе 3.

### 2. Схема `learning`

Схема уже создана в `000001_init`; миграция `000010_learning` создаёт только таблицы.

```
learning.study_plans
  id uuid PK, user_id uuid, exam_id uuid, exam_date date,
  target_score int, weekly_minutes int, status text,
  version int, last_replanned_at timestamptz, created_at, updated_at

learning.plan_weeks
  id uuid PK, plan_id uuid, week_start date, phase text, goals_json jsonb

learning.plan_items
  id uuid PK, week_id uuid, day_of_week int, kind text,
  topic_id uuid NULL, kim_number_id uuid NULL, task_count int, status text

learning.sessions
  id uuid PK, user_id uuid, exam_id uuid, kind text, variant_id uuid NULL,
  status text, started_at, deadline_at NULL, finished_at NULL,
  score_primary numeric(8,2) NULL, created_at

learning.session_items
  id uuid PK, session_id uuid, position int, task_id uuid,
  task_snapshot jsonb, max_points numeric(6,2), status text

learning.answers
  id uuid PK, session_item_id uuid UNIQUE, raw_answer text,
  normalized_answer text, is_correct boolean, awarded_points numeric(6,2),
  check_kind text, checked_at timestamptz, created_at

learning.topic_mastery
  user_id uuid, topic_id uuid, mastery numeric(4,3), attempts int, correct int,
  interval_days int, ease numeric(3,2), last_practiced_at timestamptz,
  next_review_at timestamptz, PRIMARY KEY (user_id, topic_id)

learning.kim_mastery
  user_id uuid, kim_number_id uuid, mastery numeric(4,3), attempts int,
  correct int, last_practiced_at timestamptz,
  PRIMARY KEY (user_id, kim_number_id)

learning.session_results
  session_id uuid PK, primary_score numeric(8,2), max_score numeric(8,2),
  test_score int NULL, grade int NULL, breakdown_json jsonb
```

- Все PK — UUID v7. Внешних ключей на `content`/`profile` нет; ссылки только по UUID.
- Внутри `learning` FK допустимы: `plan_weeks.plan_id`, `plan_items.week_id`, `session_items.session_id`, `answers.session_item_id`, `session_results.session_id`.
- Индексы: `study_plans (user_id, status)`, `plan_weeks (plan_id, week_start)`, `plan_items (week_id, day_of_week)`, `sessions (user_id, created_at DESC)`, `sessions (status) WHERE status = 'in_progress'`, `session_items (session_id, position) UNIQUE`, `topic_mastery (user_id)`, `kim_mastery (user_id)`.
- Частичный уникальный индекс `study_plans (user_id) WHERE status = 'active'` гарантирует один активный план.
- Статусы: план `active`/`superseded`; сессия `in_progress`/`completed`; элемент сессии `pending`/`answered`; пункт плана `pending`/`done`.

Конфликт ТЗ 5.5 и 7.4: таблицы `study_plans`, `plan_weeks`, `plan_items`, `kim_mastery`, `session_results` берутся из 5.5, потому что без них невозможно выполнить FR-LEARN-01…05; 7.4 считается неполным перечислением. `interval_days`, `ease`, `next_review_at` создаются сразу, но заполняются на этапе 5.

### 3. Снимок задания и сессия

При старте диагностики для каждого задания сохраняется `task_snapshot`:

```
{
  "task_id": "...",
  "version": 3,
  "statement_md": "...",
  "answer_spec": {...},
  "answer_display": "...",
  "difficulty": "easy",
  "kim_number_id": "...",
  "topic_id": "...",
  "max_points": 1,
  "attachments": [...]
}
```

Ответы проверяются по снимку, а не по текущей версии задания, поэтому правка банка не меняет историю (FR-CONT-09). `task_id` остаётся ссылкой на активную версию на момент старта.

Альтернатива: хранить только `task_id` и читать актуальную версию. Отвергнута — нарушает FR-CONT-09 и делает результаты невоспроизводимыми.

### 4. Формирование диагностической выборки

1. Взять последний опубликованный учебный год трека.
2. Прочитать номера КИМ и темы.
3. Прочитать публичные задания с поддерживаемыми `kind` (`number`, `text`, `digits`, `interval`), исключив задания опубликованных пробников.
4. Сгруппировать задания по номеру КИМ.
5. Для каждого номера выбрать одно задание: сначала самое простое, затем с меньшим `position` в банке; задания части 2 с `extended` не выбираются.
6. Оценить длительность: `easy` — 1 минута, `medium` — 2 минуты, `hard` — 3 минуты. Сумма — оценка длительности.
7. Если оценка превышает 45 минут, заменить выбранные задания на более простые альтернативы того же номера; если альтернатив нет, сохранить покрытие и показать оценку длительности.
8. Если хотя бы один номер КИМ не имеет подходящего задания, диагностика не стартует: возвращается ошибка «недостаточно контента» с пояснением.

Порядок заданий в сессии — по возрастанию номера КИМ, что даёт переход от базовой сложности к повышенной. Перемешивание не применяется, чтобы покрытие и порядок были воспроизводимы.

Конфликт ТЗ 4.2 (покрытие всех номеров и ≤45 минут): приоритет у покрытия, 45 минут — целевой ориентир. Это осознанное отклонение: критерий приёмки этапа прямо требует покрытия всех номеров КИМ. Оценка длительности показывается ученику до старта.

Альтернатива: случайная выборка 5–7 заданий как в демо. Отвергнута — диагностика должна покрывать все номера КИМ.

Альтернатива: жёстко ограничить 45 минутами и потерять покрытие. Отвергнута — противоречит критерию приёмки.

### 5. Проверка ответов

`learning` вызывает `grading.Check(snapshot.AnswerSpec, rawAnswer)`. Поддерживаемые `kind` определяются `grading.Supports`; `choice` и `extended` в диагностику не попадают. Результат сохраняет `normalized_answer`, `is_correct`, `awarded_points`, `check_kind`, `checked_at` и причину в `breakdown_json`. `awarded_points` — `max_points` при верном ответе и `0` при неверном. Частичные баллы для коротких ответов не начисляются.

Альтернатива: реализовать проверку внутри `learning`. Отвергнута — дублирует библиотеку и нарушает предметную нейтральность.

### 6. Освоение

Для каждой затронутой темы и каждого номера КИМ:

```
mastery_new = clamp(mastery_old * (1 - 0.3) + correct * 0.3 * difficulty_factor, 0, 1)
difficulty_factor = 1.0 / 1.1 / 1.2 для easy / medium / hard
```

- `mastery_old` при отсутствии записи — 0.
- `attempts` и `correct` увеличиваются на число ответов в сессии.
- `low_confidence` вычисляется на чтении: `attempts < 3`; отдельного поля нет.
- `last_practiced_at` обновляется временем завершения сессии.
- `interval_days`, `ease`, `next_review_at` инициализируются значениями ТЗ 5.5, но не пересчитываются до этапа 5.

Альтернатива: считать освоение только по темам. Отвергнута — FR-LEARN-03 требует и темы, и номера КИМ.

### 7. Карта пробелов и приоритет

Карта строится из тем трека (строки) и номеров КИМ (столбцы). Для ячейки берётся освоение темы и номера КИМ; если связи `kim_topics` нет, ячейка нейтральна. Состояние передаётся символом, текстом и цветом (UI-22).

Приоритет темы:

```
topic_weight = Σ(kim.max_primary_score * kim_topic.weight) / Σ(kim.max_primary_score)
confidence_factor = 1.0 при attempts >= 3, иначе 1.2
recency_factor = 1.0 + 0.2 * (1 - mastery), если last_practiced_at старше 14 дней, иначе 1.0
priority = topic_weight * (1 - mastery) * confidence_factor * recency_factor
```

Список тем для повторения сортируется по убыванию `priority`, при равенстве — по `order_index` темы. Темы без попыток попадают в начало.

Альтернатива: сортировать только по `mastery`. Отвергнута — не учитывает вес темы в первичном балле и давность.

### 8. Генерация недельного плана

- Неделя начинается в понедельник (UTC на этапе 4).
- План строится от текущей недели до недели даты экзамена включительно.
- Бюджет недели — `weekly_minutes`; он не превышается.
- Распределение по фазам: первая неделя — `diagnostics` (пункт диагностики, если она ещё не пройдена), далее `base`, затем `practice`, последняя неделя — `review`.
- Внутри недели минуты распределяются по дням с понедельника; один пункт — один день.
- Пункт содержит `kind` (`diagnostic`, `theory`, `practice`, `review`), `topic_id` или `kim_number_id`, `task_count`.
- `task_count` оценивается как `минуты пункта / 5` с минимумом 1.
- Темы берутся в порядке приоритета; при исчерпании тем цикл повторяется по кругу.
- Если цель не задана, план не создаётся, а экран предлагает задать учебную цель.
- Если дата экзамена уже прошла, план не создаётся, а экран объясняет причину.

Альтернатива: генерировать план на фиксированные 4 недели. Отвергнута — FR-LEARN-04 требует горизонт до даты экзамена.

### 9. Пересчёт плана

- Пересчёт запускается после завершения диагностики и лениво при чтении плана, если `last_replanned_at` старше 7 дней.
- Пересчёт создаёт новую версию: текущий план становится `superseded`, новый — `active` с `version + 1`.
- Прошедшие недели и завершённые пункты копируются в новую версию без изменений.
- Будущие недели генерируются заново по актуальной карте пробелов.
- Старые версии не удаляются, поэтому история сохраняется.
- Пересчёт идемпотентен в пределах одного дня: повторный вызов не создаёт новую версию, если карта пробелов не менялась.

Альтернатива: обновлять пункты на месте. Отвергнута — теряется история и усложняется сохранение завершённых пунктов.

### 10. Учебная цель и межмодульная согласованность

Учебную цель настраивает `learning`:

1. Проверяет входные данные и опубликованность трека через `ContentProvider`.
2. Сохраняет цель через `GoalProvider.SaveGoal` (модуль `profile` уже проверяет дату, балл и время).
3. Создаёт активный план в транзакции `learning`.

Транзакция `profile` и транзакция `learning` не объединяются (ТЗ 6.6). Если шаг 3 не удался, цель остаётся сохранённой; повторная настройка цели идемпотентно создаёт план. Если шаг 2 не удался, план не создаётся. UI показывает ошибку и кнопку повтора.

Альтернатива: общая транзакция через `profile`-репозиторий. Отвергнута — нарушает границы модулей.

```
GET  /app/goal                   — форма учебной цели
POST /app/goal                   — сохранение цели и создание плана
GET  /app/diagnostics            — старт диагностики
POST /app/diagnostics            — создание сессии
GET  /app/diagnostics/:id        — прохождение
POST /app/diagnostics/:id/items/:itemId — сохранение ответа
POST /app/diagnostics/:id/submit — завершение
GET  /app/diagnostics/:id/result — результат
GET  /app/gaps                   — карта пробелов

POST /app/plan/replan            — пересчёт

```

JSON-маршруты за `auth.Auth`, только для плана и диагностики из ТЗ 8.6:

```
GET   /api/plan
POST  /api/plan/replan
PATCH /api/plan/items/{id}
POST  /api/diagnostics
GET   /api/sessions/{id}
PATCH /api/sessions/{id}/items/{itemId}
POST  /api/sessions/{id}/submit

```

`POST /api/sessions` принимает только `kind = diagnostic`; остальные виды сессий отклоняются до этапов 5–6. Все изменяющие запросы требуют CSRF (API-03). JSON использует единый конверт ошибок (API-04). Владелец проверяется в Service по `userID` из контекста.

Экраны собираются из `ui.AppShell`, `ui.TodayScreen`, `ui.GapHeatmap`, `ui.Card`, `ui.Field`, `ui.Button`, `ui.EmptyState`, `ui.ResultPanel`. «Сегодня» показывает ближайший пункт плана, состояние подготовки и темы для повторения. Ошибки валидации выводятся рядом с полем и помечают поле `aria-invalid`. HTMX используется для сохранения ответа и отметки пункта; без JavaScript работают обычные формы.

Альтернатива: отдельный SPA-кабинет. Отвергнута — `AGENTS.md` требует Templ и HTMX, админка на Vue — отдельный контур.

### 12. Транзакции

- Создание сессии с элементами — одна транзакция `learning`.
- Сохранение ответа и обновление элемента — одна транзакция.
- Завершение сессии: расчёт результата, обновление освоения и пересчёт плана — одна транзакция `learning`. Пересчёт плана читает `content` до транзакции и использует уже загруженные данные внутри неё.
- Пересчёт плана — одна транзакция.
- Репозиторий не начинает транзакции; `Querier` передаётся из Service.

## Risks / Trade-offs

- **Неполное перечисление таблиц в ТЗ 7.4** → берём состав из ТЗ 5.5; фиксируем в design и миграции.
- **Конфликт покрытия и 45 минут** → приоритет покрытия, длительность — ориентир; оценка показывается до старта; тест на конфликт.
- **Недостаточно контента для покрытия** → диагностика не стартует; экран объясняет причину и предлагает вернуться позже.
- **Межмодульная согласованность цели и плана** → повторная настройка цели идемпотентна, частичный сбой не теряет цель.
- **Холодный старт освоения** → `mastery = 0`, `low_confidence` до трёх попыток, приоритет выше.
- **Производительность карты** → чтение связей `kim_topics` одним запросом по учебному году, а не по каждому номеру; индексы по `user_id`.
- **Сложность генерации плана** → простые правила распределения минут, без оптимизации; unit-тесты на границы недель и бюджет.
- **Часовой пояс** → недели в UTC на этапе 4; перенос на часовой пояс профиля — открытый вопрос.
- **Полный отчёт демо** → на этапе 4 полный отчёт относится к зарегистрированной диагностике; перенос анонимного демо — открытый вопрос, чтобы не расширять scope.
