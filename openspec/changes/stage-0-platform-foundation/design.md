## Context

См. `proposal.md` — Why. Репозиторий greenfield: Go-кода нет, `go.mod` отсутствует, `openspec/specs/` пуст. Есть только ТЗ (`docs/technical-specification.md`), `AGENTS.md` и research-материалы.

Ограничения, которые формируют подход:

- `AGENTS.md`: модульный монолит, `Handler → Service → Repository`, pgx v5, golang-migrate, ручной SQL без ORM и query builder, UUID v7, `context.Context` первым аргументом, `log/slog`, cleanenv + godotenv, запрет `os.Getenv` вне пакета конфигурации, Templ/HTMX/Pico.css, Vue SPA для админки, русский язык.
- ТЗ выбирает `gin` как HTTP-фреймворк и фиксирует переменные окружения (раздел 14.3), целевые показатели (раздел 13), инфраструктуру (раздел 14) и этап 0 (раздел 16).
- Этап 0 не содержит бизнес-логики, поэтому здесь закладываются только сквозные механизмы: конфигурация, БД, миграции, HTTP-конвейер, логирование, локальная среда, CI.

Конфликты требований и принятое разрешение:

| Конфликт | Решение |
|---|---|
| `AGENTS.md` предпочитает стандартную библиотеку, ТЗ требует Gin | Берём Gin: ТЗ имеет приоритет над «предпочтениями» AGENTS, но middleware пишем тонкими и без бизнес-логики |
| `AGENTS.md` упоминает локализацию и переводы всех языков, ТЗ и раздел «Мультиязычность» требуют только русский | Только русский, `locales/` не создаётся |
| ТЗ перечисляет переменные AI/YooKassa/rate limit, но этап 0 их не использует | Конфиг этапа 0 содержит только используемые переменные; остальные добавляются вместе с модулями (иначе появляются неиспользуемые поля и обязательные секреты на пустом месте) |

## Goals / Non-Goals

**Goals:**

- Дать единый, проверяемый при старте объект конфигурации без чтения окружения в других пакетах.
- Дать единый способ работы с БД и транзакциями, на который смогут опереться все модули.
- Сделать миграции воспроизводимыми (up/down) и проверяемыми в CI.
- Дать HTTP-фундамент с наблюдаемостью и безопасными значениями по умолчанию.
- Обеспечить локальный запуск одной командой и воспроизводимый CI.

**Non-Goals:**

- Любая бизнес-логика, доменные сущности и бизнес-таблицы.
- Аутентификация, RBAC, CSRF, rate limit (этап 1).
- Отправка писем и реальные S3-операции (этапы 1–2); MailHog и MinIO только поднимаются.
- UI-страницы на Templ, `templ generate` как обязательный шаг сборки контента (появится с первыми шаблонами).
- Метрики Prometheus и алерты (этап 10, NFR-22).
- Выбор AI-провайдера, YooKassa-интеграция.

## Decisions

### 1. Структура каталогов

Следуем ТЗ (раздел 6.2) и `AGENTS.md`:

```
cmd/
  server/main.go          — composition root (пока только каркас)
  migrate/main.go         — применение/откат миграций (embedded FS)
internal/
  shared/
    config/
    db/
    httpserver/
    logging/
    ids/
migrations/
docker/
  docker-compose.yml        — только инфраструктура
web/static/               — пока пусто, появится с UI
.env.example
Makefile
```

Альтернатива: складывать всё в `cmd/server`. Отвергнута — нарушает модульные границы и `AGENTS.md`.

### 2. Конфигурация

- `cleanenv` + `godotenv`: `.env` читается только для `APP_ENV=local` (или при наличии файла), реальные переменные окружения имеют приоритет.
- Один `Config` со вложенными группами (`App`, `HTTP`, `DB`, `Log`, `SMTP`, `S3`).
- Валидация в `Load()`: обязательные поля, парсинг длительностей/чисел, допустимые значения `LOG_LEVEL` и `APP_ENV`. Ошибка содержит имя переменной.
- На этапе 0 читаются: `APP_ENV`, `APP_BASE_URL`, `HTTP_ADDR`, `HTTP_READ_TIMEOUT_SECONDS`, `HTTP_WRITE_TIMEOUT_SECONDS`, `HTTP_SHUTDOWN_TIMEOUT_SECONDS`, `HTTP_MAX_BODY_BYTES`, `LOG_LEVEL`, `SESSION_SECRET`, `DATABASE_URL`, `DB_MAX_CONNS`, `DB_MIN_CONNS`, `MIGRATIONS_DIR`, `SMTP_*`, `S3_*`. Последние две группы нужны для compose-проверок и будут использованы на этапах 1–2; на этапе 0 они только валидируются как часть среды. Если поле не используется ни одним кодом этапа 0 — оно не добавляется.
- Добавленные относительно ТЗ переменные: `HTTP_READ_TIMEOUT_SECONDS`, `HTTP_WRITE_TIMEOUT_SECONDS`, `HTTP_SHUTDOWN_TIMEOUT_SECONDS`, `HTTP_MAX_BODY_BYTES` — нужны для проверяемых требований по таймаутам и лимиту тела. Имеют безопасные значения по умолчанию.
- `SESSION_SECRET` обязателен уже сейчас: позже он подписывает cookie и CSRF; отсутствие секрета должно ломать старт, а не продакшен позже.
- Запрет `os.Getenv` вне `internal/shared/config` проверяется линтером (`forbidigo`) в CI.

### 3. Работа с PostgreSQL

- `pgxpool` с `DB_MIN_CONNS`/`DB_MAX_CONNS`; при старте выполняется `Ping` с таймаутом.
- Транзакции — только helper в `internal/shared/db`:

```go
func WithTx(ctx context.Context, pool *pgxpool.Pool, fn func(pgx.Tx) error) error
```

  Helper делает `Begin`, `defer Rollback`, вызывает `fn`, делает `Commit`; ошибки оборачиваются через `%w`.
- Репозитории принимают интерфейс с методами `Exec/Query/QueryRow` (его реализуют и `*pgxpool.Pool`, и `pgx.Tx`), поэтому репозиторий не знает, в транзакции он или нет. Это соответствует правилу «транзакции только в Service» без введения ORM.
- Альтернатива: передавать `*pgxpool.Pool` всегда и открывать транзакцию внутри репозитория. Отвергнута — нарушает `AGENTS.md`.

### 4. Миграции

- Каталог `migrations/NNNNNN_name.up.sql` / `.down.sql`, `golang-migrate`.
- Миграции встраиваются через `//go:embed` в бинарник `cmd/migrate` (iofs source), поэтому не зависят от рабочей директории и образа.
- `cmd/migrate` поддерживает `up`, `down 1`, `version`; `make migrate-up` / `make migrate-down` вызывают его.
- Первая миграция `000001_init` создаёт схемы: `auth`, `profile`, `content`, `learning`, `ai`, `review`, `progress`, `parent`, `billing`, `notify`, `admin` (`CREATE SCHEMA IF NOT EXISTS`). `public` не создаётся и не удаляется. Down удаляет эти схемы, кроме `public`.
- Бизнес-таблицы в схемах создаются на этапах 1+ отдельными миграциями; схема-владелец появляется заранее, чтобы инфраструктурные файлы не менялись.
- Readiness: приложение использует тот же embedded FS, читает последнюю версию и сравнивает с `version` из `schema_migrations` (таблица golang-migrate в `public`). Отсутствие таблицы или расхождение → not ready с причиной. Применение миграций остаётся отдельной командой.
- Альтернатива: применять миграции при старте приложения. Отвергнута — ТЗ (OPS-04) требует отдельной операции и предсказуемого деплоя.

### 5. HTTP-сервер

- Gin в `release` режиме вне `local`; `gin.SetMode` из `APP_ENV`.
- Порядок middleware: request_id → recovery → structured logging → security headers → body limit.
- `request_id`: если клиент прислал `X-Request-Id` — принимаем (после валидации формата), иначе генерируем UUID v7. Значение кладётся в `context.Context` и в заголовок ответа.
- Recovery: логирует панику со стеком в лог (стек не отдаётся клиенту), отвечает `500` в едином формате ошибки из ТЗ (раздел 8.2) — общий конверт закладывается здесь, чтобы не менять контракт позже.
- Body limit: `http.MaxBytesReader`; превышение → `413`/`400` с кодом `bad_request`.
- Security headers: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, базовая CSP; HSTS — только когда `APP_ENV=production` и запрос пришёл по HTTPS.
- `/healthz` — не трогает БД. `/readyz` — `Ping` + проверка версии миграций.
- Graceful shutdown: `http.Server.Shutdown` с `HTTP_SHUTDOWN_TIMEOUT_SECONDS`, затем `pool.Close()`; сигналы `SIGINT`, `SIGTERM`.
- Альтернатива: `net/http` + `chi`/stdlib. Отвергнута из-за прямого требования ТЗ использовать Gin.

### 6. Логирование

- `log/slog` с `JSONHandler`, уровень из `LOG_LEVEL`, вывод в stdout.
- HTTP-middleware пишет одну запись на запрос: `method`, `path`, `status`, `duration_ms`, `request_id`, `bytes`.
- Значения заголовков `Authorization`, `Cookie`, `Set-Cookie`, а также поля с именами `password`, `token`, `secret` не логируются. Политика закреплена helper-функцией редаркции и тестом.

### 7. UUID v7

- Используем `github.com/google/uuid` (`uuid.NewV7`): проверенная реализация, уже распространена в Go-экосистеме; писать свою генерацию ради одной функции противоречит «не добавлять зависимость ради одной функции» только при наличии альтернативы в stdlib, а её нет.
- Пакет `internal/shared/ids` инкапсулирует генерацию, чтобы позже можно было заменить реализацию без правок по модулям.
- Тест проверяет версию (`uuid.Version()==7`) и монотонность по времени.

### 8. Локальная инфраструктура

`docker/docker-compose.yml`:

| Сервис | Образ | Особенности |
|---|---|---|
| `postgres` | `postgres:16` | том `pgdata`, healthcheck `pg_isready` |
| `mailhog` | `mailhog/mailhog` | порты SMTP и web UI |
| `minio` | `minio/minio` | том `miniodata`, healthcheck |
| `minio-init` | `minio/mc` | создаёт бакет `S3_BUCKET`, затем завершается |

- Go-приложение в Docker не упаковывается: локально `cmd/server` и `cmd/migrate` запускаются как обычные бинарники (или через `go run`), в production — как сервис (systemd/оркестратор). Compose поднимает только инфраструктуру, от которой зависит приложение.
- Все параметры через `.env`; никаких секретов в compose.

### 9. Makefile и CI

- `make up/down`, `migrate-up`, `migrate-down`, `test`, `lint`, `build`, `templ`.
- `make templ` — заглушка, которая выполняет `templ generate` только при наличии `.templ`-файлов; иначе печатает, что генерировать нечего.
- CI (GitHub Actions, `.github/workflows/ci.yml`): `golangci-lint` → `templ generate` + проверка `git diff --exit-code` → `go test ./...` → поднятие Postgres-сервиса, `migrate up`, `migrate down 1`, `migrate up` → `go build ./...`.
- Альтернатива: GitLab CI. Отвергнута как произвольный выбор; при необходимости workflow переносится без изменения кода (открытый вопрос ниже).

### 10. Тестовая стратегия этапа 0

- `config`: table-driven тесты полной/неполной/некорректной конфигурации.
- `db.WithTx`: тест на commit и rollback; для unit-уровня — фейковый `pgx.Tx` не нужен, тест интеграционный с реальным Postgres (в CI) + unit на обёртку ошибок.
- `httpserver`: тесты middleware (`request_id`, recovery, body limit) через `httptest`; readiness с фейковым `Pinger` и фейковым чекером миграций.
- `ids`: тест версии и монотонности.

## Risks / Trade-offs

- [Пустые схемы в первой миграции] → Если состав модулей изменится, схемы останутся неиспользуемыми. Митигация: список схем соответствует ТЗ; удаление — новой миграцией, существующие не меняются.
- [Readiness зависит от таблицы `schema_migrations`] → При нестандартном имени таблицы проверка сломается. Митигация: имя зафиксировано константой в одном пакете и покрыто тестом; при смене — правка в одном месте.
- [Gin вместо stdlib] → Дополнительная зависимость и «магия» роутинга. Митигация: тонкие middleware, никакой бизнес-логики, конверт ошибок и логирование собственные.
- [Таймауты и лимит тела добавляют переменные вне ТЗ] → Расхождение с разделом 14.3. Митигация: переменные с безопасными значениями по умолчанию, документированы в `.env.example`; ТЗ не запрещает расширять конфиг.
- [MailHog и MinIO подняты, но не используются] → Возможное впечатление мёртвой инфраструктуры. Митигация: сервисы нужны для этапов 1–2 и проверяются в compose; в коде этапа 0 нет неиспользуемых адаптеров.
- [CI-провайдер выбран предположительно] → Если репозиторий не на GitHub, workflow не запустится. Митигация: вынести конвейер в отдельный файл и подтвердить провайдера до реализации (открытый вопрос).
- [Проверка `templ generate` на этапе без шаблонов] → Формально зелёная, но ничего не проверяет. Митигация: шаг становится значимым с первыми `.templ`-файлами; логика «нет файлов → no-op» явная.

## Migration Plan

1. Создать каркас и конфигурацию, поднять локальную среду, применить первую миграцию.
2. Проверить `/healthz`, `/readyz`, логи и graceful shutdown.
3. Включить CI: линтер, тесты, применение и откат миграций, сборка.
4. Откат на этом этапе: остановить контейнеры и откатить миграцию `000001` (down), затем предыдущая версия приложения не нужна — предыдущих версий ещё нет.
