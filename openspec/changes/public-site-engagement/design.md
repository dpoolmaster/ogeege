## Context

См. `proposal.md` — Why. Текущее состояние, определяющее подход:

- Демо-диагностика уже работает: `GET /diagnostics/demo?exam=...` выдаёт 5–7 заданий, `POST /diagnostics/demo/check` проверяет все ответы сразу. Набор заданий и срок жизни задаёт подписанный cookie `demo_session` (`internal/publicsite/demo.go`), в БД ничего не пишется.
- Проверка короткого ответа вынесена в `internal/grading` и используется банком; отдельного модуля создавать не нужно.
- Публичные GET-страницы кэшируются на 60 секунд (`internal/publicsite/cache.go`), CSRF-плейсхолдер подставляется при выдаче. Демо-ответы отдаются с `Cache-Control: no-store`.
- Интерфейс к моменту реализации будет собран на компонентах этапа 3.5; здесь добавляется поведение, а не стили.
- Ограничения: Templ + HTMX, без клиентского фреймворка; базовые сценарии работают без JavaScript; ответы не сохраняются.

## Goals / Non-Goals

**Goals:**

- Дать посетителю мгновенную проверку ответа на лендинге без перехода.
- Сделать демо-диагностику пошаговой с видимым прогрессом и сохранением ответов.
- Сохранить работу без JavaScript и не хранить ответы на сервере.

**Non-Goals:**

- Сохранение черновика демо в БД, таймер, возобновление после закрытия браузера.
- Полный отчёт для зарегистрированных (этап 4).
- Изменение правил проверки, банка, статей и лид-формы.

## Decisions

### 1. Один опубликованный набор маршрутов, два представления

Добавляются маршруты:

| Метод | Маршрут | Назначение |
|---|---|---|
| `POST` | `/hx/tasks/:taskId/check` | HTMX-фрагмент результата проверки на лендинге |
| `POST` | `/diagnostics/demo/step` | Полная страница шага (без JS) |
| `POST` | `/hx/demo/step` | HTMX-фрагмент шага |

`POST /diagnostics/demo/check` и `POST /bank/:taskId/check` остаются без изменений. Фрагменты возвращают только компонент, а не layout; полная страница шага использует тот же обработчик с признаком `HX-Request`.

Альтернативы: отдельные JSON-эндпоинты и клиентский рендер (противоречит HTMX и работе без JS), один универсальный `/hx/check` (смешивает банк и лендинг). Отвергнуты.

### 2. Состояние демо переносится в форме

Токен `demo_session` по-прежнему задаёт `TaskIDs`, `ExamYearID`, `IssuedAt`, `Nonce`. Ответы передаются скрытыми полями `answer_<taskID>` вместе с `step`. Сервер:

1. проверяет подпись и срок токена;
2. отбрасывает поля, чьи `taskID` отсутствуют в токене;
3. ограничивает `step` диапазоном `[1, len(TaskIDs)]`;
4. считает прогресс по числу непустых ответов;
5. на последнем шаге передаёт накопленные ответы в существующую проверку.

Так ответы не попадают в БД, токен не растёт, а переход назад сохраняет значения, потому что все предыдущие ответы уже есть в форме.

Альтернативы: хранить ответы в подписанном cookie (растёт размер, лимит 4 КБ), писать черновик в БД (нарушает «результат не сохраняется» и требует миграций), `localStorage` (ломает работу без JS). Отвергнуты.

### 3. Задание для лендинга выбирается детерминированно

Сервис берёт первое опубликованное публичное задание трека с автоматической проверкой в стабильном порядке (`ORDER BY kim_number, id`). Блок не показывается, если задания нет. Это делает страницу кэшируемой и не требует случайности на каждый запрос.

Альтернатива: случайное задание (ломает кэш и воспроизводимость тестов). Отвергнута.

### 4. Кэширование

Лендинг и статьи остаются в общем TTL-кэше. Фрагменты и шаги демо не проходят через `renderCached` и отдаются с `Cache-Control: no-store`. CSRF-плейсхолдер в кэшированном лендинге уже заменяется при выдаче, поэтому форма проверки на закэшированной странице работает.

### 5. Доступность и фокус

Результат проверки рендерится в контейнер с `role="status"` (верно) или `role="alert"` (неверно). После HTMX-подмены шага фокус переносится на заголовок шага через `data-autofocus` и обработчик `htmx:afterSwap` в `public.js`. Индикатор прогресса — нативный `<progress>` с текстовой подписью «шаг N из M».

### 6. Ограничение частоты и CSRF

Проверка на лендинге и шаги демо используют существующий middleware ограничения частоты и требуют CSRF-токен. Неверный или отсутствующий токен — отказ без выполнения проверки.

## Risks / Trade-offs

- **Подмена ответов в скрытых полях** → результат демо неавторитетен и не сохраняется; сервер отбрасывает неизвестные `taskID`, ограничивает шаг и не доверяет клиентским данным сверх проверки ответов.
- **Рост числа маршрутов** → фрагменты сгруппированы под `/hx/`, полный маршрут один; контракты банка не меняются.
- **Кэш отдаёт устаревший блок проверки** → TTL 60 секунд уже принят для лендинга; фрагменты не кэшируются.
- **Фокус после подмены** → перенос фокуса выполняется только при наличии `data-autofocus`; без JS страница перезагружается штатно.
- **Дублирование логики шага** → полная страница и фрагмент используют один метод сервиса и один шаблон шага.

## Migration Plan

1. Реализовать после этапа 3.5, чтобы использовать компоненты дизайн-системы.
2. Добавить маршруты и методы сервиса; существующие маршруты не меняются.
3. Перевести демо на пошаговый режим, сохранив `POST /diagnostics/demo/check` для совместимости.
4. Откат: удалить новые маршруты и вернуть прежний шаблон демо; миграций нет, данные не затрагиваются.
