## Context

См. `proposal.md` — Why. Этап 0 уже дал рабочую основу: конфигурация (`internal/shared/config`), пул `pgx v5` и helper транзакций (`internal/shared/db`), миграции с UP/DOWN, HTTP-сервер на Gin с middleware (`internal/shared/httpserver`), `slog`, генерацию UUID v7 (`internal/shared/ids`) и общий конверт ошибок (`AbortWithError`). Схемы модулей созданы миграцией `000001_init`, но бизнес-таблиц нет.

Ограничения, формирующие подход:

- `AGENTS.md`: модульный монолит, `Handler → Service → Repository`, pgx v5 и ручной SQL без ORM и query builder, транзакции только в Service, UUID v7, `context.Context` первым аргументом, `log/slog`, запрет `os.Getenv` вне пакета конфигурации, интерфейсы объявляет потребитель, сборка зависимостей только в `cmd/server/main.go`, только русский язык.
- Границы модулей (ТЗ 6.3): у каждого модуля своя схема; запрещены FK и JOIN между схемами; ссылки только по UUID; чтение чужого модуля только через интерфейс его сервиса.
- ТЗ 6.6: межмодульные операции не выполняются в одной транзакции; согласованность через outbox или eventual consistency.
- ТЗ 5.2 и 7.2 описывают таблицы `auth`; ТЗ 5.3 задаёт таблицы `profile`, но SQL в разделе 7 для `profile` отсутствует — таблицы выводятся из 5.3.
- ТЗ 5.12 задаёт `notify`, но этап 1 использует только email-часть (outbox и шаблоны); in-app и отписка — этап 10.

Конфликты требований и принятое решение:

| Конфликт | Решение |
|---|---|
| `AGENTS.md` упоминает локализацию и переводы всех языков; ТЗ и раздел «Мультиязычность» требуют только русский | Только русский; `locales/` не создаётся, тексты писем и страниц — на русском |
| ТЗ 7.2 даёт SQL только для `auth.users` и `auth.sessions`, а 5.2 перечисляет ещё `email_verifications`, `password_resets`, `login_attempts` | Создаём все таблицы из 5.2; для отсутствующих в 7.2 структуру выводим из назначения и общих правил раздела 7.1 |
| В разделе 7 нет SQL для `profile` | Таблицы `profile.profiles`, `profile.consents`, `profile.study_goals`, `profile.settings` строятся по 5.3 и 7.1 |
| `platform-foundation` ещё не заархивирован в `openspec/specs/`, поэтому нельзя использовать `MODIFIED` | Расширение конфигурации и HTTP-конвейера (CSRF, rate limit) фиксируется поведением capability `auth`, базовую спеку не трогаем |
| `AGENTS.md` требует CSRF и rate limit в `shared/httpserver`, но этап 1 — первый потребитель | Реализуем как middleware в `shared/httpserver`, а их поведение описываем в `auth`, чтобы не создавать дублирующую capability |

## Goals / Non-Goals

**Goals:**

- Дать безопасную аутентификацию с серверными сессиями, Argon2id, одноразовыми хешированными токенами и нейтральными ответами.
- Дать RBAC-проверку на уровне middleware с объявлением требуемой роли у маршрута.
- Дать профиль ученика с согласиями, проверкой возраста, целями и настройками.
- Дать минимальный, надёжный email-контур через outbox без общих транзакций между схемами.
- Сохранить модульные границы: `auth`, `profile`, `notify` не импортируют repository друг друга.

**Non-Goals:**

- In-app уведомления, отписка, напоминания, недельные отчёты (этап 10).
- Публичные страницы, SEO, лид-формы (этап 3).
- Админка и управление пользователями через UI (этап 2); здесь только хранение ролей и серверная проверка прав.
- Платежи, подписки и сохранение платёжных записей при удалении аккаунта (этап 9).
- Второй фактор, OAuth, вход по телефону.
- Метрики Prometheus и нагрузочные тесты (этап 10).

## Decisions

### 1. Структура модулей и границы

```
internal/
  auth/
    handler.go      — HTTP /api/auth/*, Templ-страницы входа/регистрации
    service.go      — сценарии, транзакции, проверка прав
    repository.go   — SQL по схеме auth
    entity.go       — User, Session, Token
    dto.go          — входные/выходные структуры
    middleware.go   — аутентификация и проверка роли
  profile/
    handler.go
    service.go
    repository.go
    entity.go
    dto.go
  notify/
    handler.go      — (нет публичных маршрутов на этом этапе)
    service.go      — постановка в outbox
    repository.go   — SQL по схеме notify
    worker.go       — воркер отправки
    entity.go
  shared/
    mailer/         — SMTP-клиент (stdlib net/smtp)
    clock/          — абстракция времени
    render/         — рендер Templ и layout
```

`auth` объявляет интерфейс постановки письма (`EmailEnqueuer`), который реализует `notify`. `profile` объявляет интерфейс чтения пользователя и роли (`UserProvider`), который реализует `auth`. Связи собираются только в `cmd/server/main.go`.

Альтернатива: `profile` читает `auth.users` напрямую по UUID. Отвергнута — нарушает запрет на доступ к чужой схеме.

### 2. Схема и таблицы `auth`

- `auth.users`: `id uuid PK`, `email text`, `password_hash text`, `role text`, `status text`, `email_verified_at`, `created_at`, `updated_at`; уникальный индекс по `lower(email)`.
- `auth.sessions`: `id uuid PK`, `user_id uuid`, `token_hash bytea`, `user_agent text`, `ip inet`, `expires_at`, `revoked_at`, `last_seen_at`, `created_at`; индексы по `user_id` и уникальный по `token_hash`.
- `auth.email_verifications`: `id uuid PK`, `user_id uuid`, `token_hash bytea`, `expires_at`, `consumed_at`, `created_at`; индекс по `user_id`.
- `auth.password_resets`: те же поля, что у `email_verifications`.
- `auth.login_attempts`: `id uuid PK`, `email text`, `ip inet`, `success bool`, `created_at`; индекс по `(lower(email), ip, created_at)`.

Ограничения роли и статуса реализуются `CHECK`-констрейнтами (`role IN (...)`, `status IN (...)`), а не отдельными enum-типами, чтобы миграции оставались простыми. Внешних ключей между схемами нет; `user_id` — просто UUID. FK внутри одной схемы (`sessions.user_id → auth.users.id`) допустим, но не обязателен; выбираем FK внутри схемы для целостности.

### 3. Схема и таблицы `profile`

- `profile.profiles`: `id uuid PK`, `user_id uuid UNIQUE`, `first_name`, `last_name`, `birth_date date`, `grade`, `timezone`, `contacts jsonb`, `created_at`, `updated_at`.
- `profile.consents`: `id uuid PK`, `user_id uuid`, `kind text`, `granted bool`, `document_version text`, `granted_at`, `ip inet`; индекс по `(user_id, kind)`.
- `profile.study_goals`: `id uuid PK`, `user_id uuid`, `exam_id uuid`, `exam_date date`, `target_score int`, `weekly_minutes int`, `updated_at`; история — новые строки с `created_at`, текущая цель определяется по последней записи.
- `profile.settings`: `id uuid PK`, `user_id uuid UNIQUE`, `email_notifications bool`, `weekly_report bool`, `created_at`, `updated_at`.

`exam_id` — UUID из модуля `content`, без FK между схемами. На этапе 1 список треков ещё не управляется, поэтому `exam_id` принимается как валидный UUID и не проверяется через `content`; проверка появится на этапе 2.

Альтернатива: одна таблица `profile.profiles` с JSON-полями для целей и настроек. Отвергнута — усложняет запросы и валидацию, противоречит «простота и явность».

### 4. Пароли и токены

- Пароли — Argon2id через `golang.org/x/crypto/argon2`; параметры фиксируются константами (память 64 МиБ, время 1, потоки 4, соль 16 байт, ключ 32 байта) и кодируются в PHC-строку. Параметры выносятся в константы пакета `auth`, чтобы не плодить конфиг.
- Сессионный токен — 32 случайных байта (`crypto/rand`), клиенту отдаётся base64url; в БД хранится SHA-256 от токена. Поиск сессии — по хешу.
- Токены подтверждения и сброса — 32 случайных байта, в БД только SHA-256, одноразовые через `consumed_at`.
- Сравнение хешей — константное время.

Альтернатива: JWT вместо серверных сессий. Отвергнута — ТЗ 5.2 требует отзыв сессий, а отзыв JWT требует дополнительного хранилища; серверные сессии проще и соответствуют FR-AUTH-09.

### 5. CSRF

- Double-submit: при выдаче сессии сервер устанавливает cookie с CSRF-токеном (не `HttpOnly`, `SameSite=Lax`) и включает тот же токен в форму/ответ; изменяющий запрос должен прислать токен в заголовке или поле формы, совпадающий с cookie.
- Дополнительно токен подписывается HMAC на `SESSION_SECRET` и привязывается к идентификатору сессии, чтобы исключить подмену.
- Middleware `CSRF` пропускает `GET/HEAD/OPTIONS`, для остальных методов проверяет токен и при ошибке возвращает `403 forbidden`.

Альтернатива: synchronizer token в серверной сессии. Отвергнута — double-submit проще для HTMX-форм и не требует дополнительной таблицы; привязка HMAC закрывает основной риск.

### 6. Ограничение частоты запросов

- In-memory limiter по ключу (IP для общих маршрутов, IP+email для входа) с фиксированным окном и настраиваемыми лимитами `RATE_LIMIT_LOGIN_PER_MIN` и `RATE_LIMIT_API_PER_MIN`.
- Дополнительно `auth.login_attempts` в БД считает неудачи за 15 минут для правила 5 попыток; БД-проверка устойчива к перезапуску процесса.
- In-memory limiter не разделяется между инстансами; это допустимо для MVP с одним инстансом и фиксируется в рисках.

Альтернатива: rate limit в Redis. Отвергнута — нет Redis в инфраструктуре этапа 0, а один инстанс достаточен.

### 7. Межмодульный email через outbox

Поток регистрации:

```
auth.Service.Register
  └─ db.WithTx:
       insert auth.users
       insert auth.email_verifications
       notify.Enqueue(tx, ...)        <-- notify пишет в notify.outbox в ЭТОЙ ЖЕ транзакции
  └─ после commit: worker подхватывает outbox
```

`notify.Enqueue` принимает `db.Querier` (пул или `pgx.Tx`) и пишет в `notify.outbox` в транзакции вызывающего модуля. Это единственное место, где `notify` участвует в чужой транзакции; сам `notify` транзакцию не открывает. Транзакция остаётся в `auth.Service`, как требует `AGENTS.md`.

Воркер `notify` раз в 10 секунд забирает пачку писем через `SELECT ... FOR UPDATE SKIP LOCKED`, отправляет через `mailer`, обновляет `status`, `attempts`, `last_error`, `sent_at`. Повторы — до 5 с экспоненциальной задержкой (`scheduled_at`).

Альтернатива: `auth` коммитит, затем отдельным вызовом ставит в outbox. Отвергнута — при падении между коммитом и постановкой письмо теряется.

### 8. HTTP-маршруты и UI

- JSON: `/api/auth/register`, `/login`, `/logout`, `/verify-email`, `/resend-verification`, `/password/reset-request`, `/password/reset`, `/password/change`; профиль: `/api/me`, `/api/me/profile`, `/api/me/goals`, `/api/me/settings`, `/api/me/delete-request` (ТЗ 8.4–8.5).
- Templ-страницы: `/login`, `/register`, `/verify-email`, `/password/reset` с Pico.css. Формы отправляют POST на JSON-маршруты через HTMX и получают либо редирект, либо фрагмент с ошибкой в едином конверте.
- Middleware `Auth` кладёт пользователя в контекст; middleware `RequireRole(...)` проверяет роль и возвращает `403` при несоответствии.
- Неаутентифицированный запрос к защищённому маршруту → `401 unauthorized`.

Альтернатива: только JSON API без Templ. Отвергнута — ТЗ 16 (задача 1.10) требует страницы входа и регистрации на Templ.

### 9. Удаление аккаунта

- `POST /api/me/delete-request` фиксирует запрос и запускает обезличивание: email заменяется на плейсхолдер, персональные поля профиля очищаются, сессии отзываются, токены удаляются.
- Платёжные записи на этом этапе отсутствуют, поэтому требование «сохранить по закону» реализуется как задел: обезличивание не удаляет строки, а очищает персональные поля.
- Полное физическое удаление по политике хранения — вне этапа.

### 10. Конфигурация и общие компоненты

- Новые переменные: `RATE_LIMIT_LOGIN_PER_MIN`, `RATE_LIMIT_API_PER_MIN` (обязательные, целые, > 0). Добавляются в `internal/shared/config` и `.env.example`.
- `shared/clock` — интерфейс `Now() time.Time`, реализация на `time.Now`; все проверки сроков идут через него, чтобы тесты не зависели от времени.
- `shared/mailer` — SMTP-клиент на `net/smtp` с поддержкой `SMTP_TLS`, таймаутом и отправителем `SMTP_FROM`; интерфейс `Sender` для подмены в тестах.
- `shared/render` — рендер Templ-компонентов и общий layout; ошибки рендера логируются без пользовательских данных.

### 11. Тестовая стратегия

- `auth`: table-driven тесты валидации email/пароля, Argon2id round-trip, истечение и одноразовость токенов, лимит попыток, отзыв сессий, нейтральность ответов, CSRF accept/reject, RBAC allow/deny.
- `profile`: тесты расчёта возраста, обязательности даты рождения, фиксации согласий, истории целей, обезличивания.
- `notify`: тесты повторов, исчерпания попыток, идемпотентности, отсутствия токенов в логах; `Sender` подменяется фейком.
- Интеграционные тесты на реальном PostgreSQL: регистрация → подтверждение → вход; сброс пароля → отзыв сессий; RBAC на защищённых маршрутах.

## Risks / Trade-offs

- [In-memory rate limit не разделяется между инстансами] → Для MVP один инстанс; при горизонтальном масштабировании перенести счётчики в PostgreSQL или Redis (открытый вопрос ниже).
- [Double-submit CSRF слабее synchronizer token при XSS] → CSP и экранирование Templ снижают риск XSS; токен привязан HMAC к сессии; при необходимости перейти на серверный токен.
- [Argon2id с фиксированными параметрами может быть тяжёлым для слабого сервера] → Параметры в одном месте, покрыты бенчмарком; при необходимости вынести в конфиг.
- [`exam_id` в целях не проверяется через `content`] → На этапе 1 треков ещё нет; проверка появится на этапе 2. Риск ограничен: неверный UUID не ломает план, так как план — этап 4.
- [Обезличивание без удаления платёжных записей] → На этапе 1 платежей нет; при появлении billing (этап 9) добавить сохранение обезличенных платёжных записей.
- [Воркер отправки в одном процессе с HTTP-сервером] → При падении процесса письма остаются в outbox и отправятся после рестарта; at-least-once доставка компенсируется идемпотентностью.
- [Templ добавляет шаг генерации в сборку] → `make templ` уже есть с этапа 0; CI проверяет отсутствие diff после генерации.

## Migration Plan

1. Добавить миграции `000002_notify`, `000003_auth`, `000004_profile` с UP и DOWN; применить на чистой БД, проверить `up → down 1 → up`.
2. Реализовать `shared/clock`, `shared/mailer`, `shared/render` и middleware `CSRF`/`RateLimit`; покрыть тестами.
3. Реализовать `notify` (repository, service, worker) и проверить отправку в MailHog.
4. Реализовать `auth` (repository, service, middleware, JSON-маршруты, Templ-страницы) и покрыть сценарии.
5. Реализовать `profile` (repository, service, маршруты) и покрыть сценарии.
6. Собрать зависимости в `cmd/server/main.go`, запустить воркер `notify`.
7. Откат: остановить приложение, откатить миграции `000004`, `000003`, `000002` в обратном порядке; данные этапа 1 удаляются вместе со схемами-таблицами, схемы этапа 0 остаются.

## Open Questions

- Нужен ли `RATE_LIMIT_LOGIN_PER_MIN` отдельно от БД-правила «5 неудач за 15 минут» или достаточно одного механизма? По умолчанию оставляем оба: middleware ограничивает всплеск, БД — устойчивое окно. Решение не меняет контракты.
- Горизонтальное масштабирование и общий rate limit — вне MVP; перенос счётчиков в PostgreSQL рассматривается на этапе 10 вместе с нагрузочными тестами.
