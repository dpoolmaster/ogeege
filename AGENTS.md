# О проекте

Образовательная платформа по подготовке школьников к сдаче ОГЭ и ЕГЭ.

MVP содержит математические треки, но ядро платформы предметно-нейтрально: новый предмет (физика, информатика, русский язык) добавляется данными и, при необходимости, отдельной стратегией проверки ответов, без переписывания учебного цикла. См. раздел «Предметная нейтральность».

Основные возможности:

- Три учебных трека в MVP: ОГЭ математика, ЕГЭ математика (профиль), ЕГЭ математика (база); новые треки и предметы добавляются через админку.
- Публичный контур: SEO-лендинги треков, открытый банк заданий, статьи и разборы, демо-диагностика без регистрации, лид-формы.
- Учётные записи: регистрация по email с подтверждением, вход, сессии, сброс и смена пароля, ограничение попыток.
- Профиль ученика: персональные данные, согласия, настройки, учебные цели.
- Онбординг: выбор трека, даты экзамена, целевого балла и недельного времени.
- Диагностика с построением карты пробелов по темам и номерам КИМ.
- Персональный недельный план подготовки с пересчётом по результатам.
- Теория в виде текстовых материалов.
- Банк заданий с фильтрами и тематическая практика с автопроверкой части 1.
- Пробники с серверным таймером и структурой реального экзамена.
- Проверка части 2: AI-черновик и очередь методиста (human-in-the-loop), апелляции.
- Разбор ошибок и рекомендации по повторению.
- Статистика прогресса и прогноз первичного/тестового балла или оценки.
- Кабинет родителя: привязка к ученику, прогресс, недельные отчёты.
- Freemium: бесплатные лимиты и подписка на трек с оплатой через YooKassa.
- Админка (Vue SPA): контент, задания, варианты, рубрики, шкалы перевода, промпты, очередь review, пользователи, подписки, аудит.
- Email- и in-app-уведомления через outbox.
- Роли: ученик, родитель, методист, администратор.

# Предметная нейтральность

Предмет и трек — это данные, а не код. Учебный цикл (`learning`, `progress`, `review`, `billing`, `notify`) не должен знать, к какому предмету относится трек.

Правила:

- Запрещено ветвление бизнес-логики по предмету или коду трека (`if subject == "math"`, `switch exam.Code`). Предметная специфика выражается данными.
- Трек задаётся записью в `content.exams` (`code`, `title`, `subject`); структура экзамена, темы, теория, задания, рубрики и шкалы — тоже данные в БД.
- Специфика проверки ответа живёт в `answer_spec.kind` и в стратегии `grading`, а не в учебном цикле. Новый тип ответа = новый чекер в реестре стратегий + unit-тесты; `learning` при этом не меняется.
- Промпты AI и рубрики части 2 хранятся и версионируются в БД и привязываются к предмету/типу ответа, а не к коду.
- Публичные маршруты треков строятся от `exam.code`; отдельные захардкоженные пути для конкретного предмета не добавляются.
- Поддержка формул LaTeX опциональна на уровне трека/предмета: отсутствие формул не должно ломать валидацию контента.
- Новый предмет не требует новых модулей и миграций, если он укладывается в существующие типы ответов. Если нужен новый тип — добавляется только стратегия проверки.

# Модульные границы

Каждый модуль:

- владеет своими таблицами;
- владеет своей бизнес-логикой;
- владеет своими repository.

Запрещено:

- импортировать repository другого модуля;
- обращаться напрямую к таблицам другого модуля;
- делать SQL JOIN между схемами;
- создавать Foreign Key между схемами модулей.

---

# Взаимодействие между модулями

Модули общаются только через интерфейсы.

Интерфейс объявляет потребитель.

Пример:

```go
type UserProvider interface {
    GetUser(ctx context.Context, id uuid.UUID) (*User, error)
}
```

Не создавать общие интерфейсы "на всякий случай".

---

# Handler

Handler отвечает только за:

- HTTP;
- чтение запроса;
- DTO;
- валидацию входных данных;
- вызов Service;
- формирование ответа.

Handler НЕ содержит:

- бизнес-правила;
- SQL;
- работу с другими модулями.

---

# Service

Service содержит бизнес-логику.

Service отвечает за:

- бизнес-правила;
- сценарии использования;
- транзакции;
- координацию действий.

Service НЕ должен знать:

- Gin;
- HTTP;
- JSON;
- HTML.

---

# Repository

Repository отвечает только за PostgreSQL.

Repository содержит:

- SQL;
- выполнение запросов;
- Scan;
- преобразование результата в entity.

Repository НЕ содержит:

- бизнес-логику;
- HTTP;
- вызовы других модулей.

---

# SQL

SQL пишется вручную.

SQL должен быть:

- читаемым;
- простым;
- явным.

Пример:

```go
const getCourseQuery = `
SELECT
    id,
    title,
    description
FROM courses.course
WHERE id = $1
`
```

Не скрывать SQL за генераторами.

# Definition of Done

Задача выполнена только если:

- код компилируется;
- нет dead code;
- нет TODO/FIXME;
- нет неиспользуемых импортов;
- архитектура не нарушена;
- ошибки обработаны;
- новые тексты локализованы;
- добавлены переводы всех языков;
- миграции добавлены при изменении БД;
- справка раздела обновлена при изменении его поведения или полей;
- добавление нового трека или предмета не потребовало правок учебного цикла (см. «Предметная нейтральность»);
- нет лишних зависимостей;
- код соответствует Go style.

Перед завершением задачи агент должен проверить:

- Не нарушены ли границы модулей?
- Не попала ли бизнес-логика в Handler?
