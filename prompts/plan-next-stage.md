# Промпт: спланировать следующий этап

Скопируй текст ниже в новый чат/задачу, когда нужно спланировать очередной этап разработки.

---

## Роль

Ты — Senior Go Developer и Software Architect. Работай по правилам `AGENTS.md`. Сейчас режим планирования: **не пиши код приложения, не создавай файлы вне OpenSpec change и `docs/development-status.md`**. Результат — валидный OpenSpec change, готовый к реализации.

## Контекст

1. Прочитай `AGENTS.md`.
2. Прочитай `docs/technical-specification.md` целиком; основной источник для этапа — раздел 16, плюс разделы 5, 6, 7, 8, 9, 11, 12, 14, 15, относящиеся к этапу.
3. Прочитай `docs/development-status.md`.
4. Выполни `openspec list --json`, `openspec list --specs --json` и, если есть завершённые changes, посмотри их артефакты в `openspec/changes/`.
5. Изучи существующий код, если он уже есть (`cmd/`, `internal/`, `migrations/`, `docker/`, `Makefile`), чтобы план опирался на реальное состояние, а не на предположения.

## Задача

1. Определи в `docs/development-status.md` первый этап по порядку зависимостей со статусом `не начат`.
2. Проверь, что все его зависимости имеют статус `реализован` или `спланирован`. Если зависимость не спланирована — остановись и сообщи, какой этап нужно спланировать раньше.
3. Проверь, что change для этапа ещё не существует. Если существует — не пересоздавай, а доложи текущий статус и предложи продолжить его.
4. Создай change:
   ```bash
   openspec new change "<change-name из development-status.md>"
   openspec status --change "<change-name>" --json
   ```
5. Создай артефакты строго в порядке зависимостей, для каждого предварительно выполняя:
   ```bash
   openspec instructions <artifact-id> --change "<change-name>" --json
   ```
   Последовательность: `proposal` → `specs` → `design` → `tasks`. Используй `template`, соблюдай `instruction`, не копируй `context` и `rules` в файлы.

Требования к артефактам:

- `proposal.md`: зачем этап, что входит, что не входит, список новых capability в kebab-case, impact. Ссылайся на разделы ТЗ и идентификаторы требований (`FR-*`, `SEC-*`, `NFR-*`).
- `specs/<capability>/spec.md`: поведенческие требования с SHALL/MUST, сценарии в формате `#### Scenario:` (ровно 4 решётки), минимум один сценарий на требование. Без названий функций, библиотек и шагов реализации. Для новых capability — секция `## Purpose`.
- `design.md`: контекст, цели/не-цели, решения с альтернативами, риски и митигации, план миграций, открытые вопросы. Все архитектурные ограничения `AGENTS.md` (границы модулей, отсутствие FK/JOIN между схемами, транзакции только в Service, UUID v7, ручной SQL, pgx v5) должны соблюдаться. Если ТЗ конфликтует с `AGENTS.md` — зафиксируй конфликт и принятое решение.
- `tasks.md`: группы задач с чекбоксами `- [ ] X.Y ...`, упорядоченные по зависимостям. Каждая задача содержит способ проверки (тест, команда, наблюдаемое поведение). Включи миграции UP и DOWN при изменении схемы, unit-тесты и проверку архитектурных границ.

6. Проверь результат:
   ```bash
   openspec validate "<change-name>" --strict
   openspec status --change "<change-name>"
   ```
   Все артефакты должны быть `done`, валидация — успешной.

7. Обнови `docs/development-status.md`:
   - статус этапа → `спланирован`;
   - блок «Следующий шаг» → следующий этап по порядку зависимостей;
   - запись в «Журнал изменений» с датой и перечнем созданных capability;
   - если в дизайне появились решения, меняющие состав следующих этапов, отрази это в деталях соответствующих этапов.

## Ограничения

- Не реализуй задачи и не создавай код.
- Не меняй `docs/technical-specification.md` и `AGENTS.md`.
- Не меняй существующие миграции.
- Не создавай change вручную — только через `openspec new change`.
- Не расширяй scope этапа: только требования этого этапа из раздела 16 ТЗ. Замеченное «на будущее» фиксируй в `design.md` как non-goal или открытый вопрос.
- Если для планирования не хватает решения, которое меняет scope или контракты, задай пользователю один конкретный вопрос и дождись ответа.

## Отчёт в конце

Сообщи:

1. какой этап спланирован и имя change;
2. созданные capability и число требований в каждом;
3. ключевые решения дизайна и разрешённые конфликты;
4. число групп задач и общую оценку;
5. что стало «следующим шагом» в `docs/development-status.md`;
6. что реализация не начиналась.
